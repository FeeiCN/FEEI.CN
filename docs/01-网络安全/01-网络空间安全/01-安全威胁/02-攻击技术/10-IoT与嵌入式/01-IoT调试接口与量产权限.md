一台设备的 Web 管理后台要求密码，并不意味着主板上的调试通道也受同一套认证保护。攻击者可能买到同型号设备、接触退役样机或短暂拆开现场设备，再利用研发期间保留的接口读取日志、暂停处理器或改写启动状态。决定风险的是接口开放后的实际能力，以及这些能力能否影响其他设备。

## 实操：识别 UART、读取芯片信息并备份真实固件

本节使用 ESP32-DevKitC V4、ESP32-WROOM 模组、4 MiB Flash 开发板，通过板载 USB—串口芯片连接。操作真实 Flash 和启动日志，不需要另写目标程序。未知产品拆机时先识别地线与电平；3.3 V TTL 串口不能直接接 RS-232 或 5 V 信号。ESP32-C3、S3 的型号和引脚不按本节照搬。

### 安装工具并确定端口

在电脑上按[工具环境](./IoT安全.md#lab-environment)安装 esptool v4，插入开发板：

```bash
python -m serial.tools.list_ports -v
```

对比拔插前后的列表，找到新增串口。macOS 通常形如 `/dev/cu.usbserial-xxxx`，Linux 通常是 `/dev/ttyUSB0`。把下面的值换成实际端口：

```bash
export IOT_PORT=/dev/cu.usbserial-xxxx
python -m esptool --chip esp32 --port "$IOT_PORT" chip_id
python -m esptool --chip esp32 --port "$IOT_PORT" flash_id
```

保存芯片型号、修订和 Flash 容量。只有结果确为 ESP32、容量 4 MiB，才使用下一条长度；容量不同则按实际容量读取。连接失败与芯片禁止读取是不同结果，先排除接线、端口占用和下载模式问题。

### 读取副本并观察系统是否接受输入

```bash
python -m esptool --chip esp32 --port "$IOT_PORT" read_flash 0 0x400000 backup-4m.bin
wc -c backup-4m.bin
shasum -a 256 backup-4m.bin
python -m serial.tools.miniterm "$IOT_PORT" 115200
```

副本应为 4194304 字节。进入 miniterm 后按 EN/RESET，保存完整启动日志，按 `Ctrl+]` 退出。记录是否出现 ROM、Bootloader、内核或应用输出，是否出现登录提示或已安装系统的 REPL。按回车没有交互提示，只能写“日志可读”，不能写成取得 Shell。

对真实路由器的 TTL 焊盘，先用示波器或逻辑分析仪确认启动时的 TX 信号和电平，再用 USB—TTL 的 RX 接设备 TX、GND 接 GND；需要交互时才连接对向 TX。开发板上的 esptool 下载协议不能套用到任意路由器 UART。

### 判断读取结果与排障

`read_flash` 被明确拒绝时，保留错误及安全配置；读取成功也可能得到加密内容，继续到[存储分析](./03-IoT存储密钥与设备克隆.md)识别格式。不要用乱码判断芯片已经加密。

连接超时先关闭 IDE、串口监视器，再按住 BOOT、轻按 EN，连接后松开 BOOT。日志乱码先核对波特率。JTAG/SWD 需要对应调试器与针脚，本节没有执行处理器调试。命令依据 [esptool v4 文档](https://docs.espressif.com/projects/esptool/en/release-v4/esp32/esptool/basic-commands.html)。

### 使用 ESP-Prog 核对 JTAG 访问

同一块经典 ESP32 开发板可继续使用 ESP-Prog 的 JTAG 通道。安装 ESP-IDF v5.3.4 工具环境提供的 Espressif OpenOCD，先运行 `openocd --version`，确认脚本目录包含下面的接口与目标配置。USB—串口的 TX/RX 不能代替 JTAG 线。

| ESP32 引脚 | JTAG 信号 |
| --- | --- |
| GPIO12 / MTDI | TDI |
| GPIO13 / MTCK | TCK |
| GPIO14 / MTMS | TMS |
| GPIO15 / MTDO | TDO |

按[官方接线说明](https://docs.espressif.com/projects/esp-idf/en/v5.3.4/esp32/api-guides/jtag-debugging/configure-other-jtag.html)连接同名信号、参考电压与公共地，核对这些 GPIO 没有被板上其他外设占用。在专用样机上先只做初始化、目标枚举与退出：

```bash
openocd -f interface/ftdi/esp32_devkitj_v1.cfg -f target/esp32.cfg \
  -c "init; targets; shutdown"
```

识别到适配器不等于识别到芯片 TAP；识别到目标也不等于能够读取所有地址。保存每一步的输出，结合 `JTAG_DISABLE` 与启动安全状态解释结果。配置文件与故障排查见 [ESP-IDF JTAG 说明](https://docs.espressif.com/projects/esp-idf/en/v5.3.4/esp32/api-guides/jtag-debugging/tips-and-quirks.html)。

若需要继续验证处理器控制，在同一配置上将命令改为 `init; halt; reg pc; resume; shutdown`，检查能否暂停、读取程序计数器并恢复；这会短暂停止应用，只用于已断开实际执行器的研究板。内存读取需要先从对应 ELF、链接映射和芯片内存图确认地址及区域，再选择目标范围；本文未连接实机验证以上 JTAG 操作。

## 成立前提与能力变化

物理调试利用至少需要接触到目标接口，芯片或固件仍允许相应操作，并且该操作能到达所需内存、配置或执行上下文。日志读取、Flash 写入和任意代码执行应分别判定。典型链路是“接口访问 → 取得调试能力 → 读出或修改目标对象 → 验证新增权限”；仅识别接口不构成链路完成。

## UART 输出、系统控制台和处理器调试是三件事

UART 是字节传输通道。启动日志通过 UART 输出，只能证明系统向外发送信息；是否接受输入、是否运行登录程序、是否开放 Bootloader 命令，需要分别验证。日志本身也可能暴露网络配置、令牌或崩溃现场，但这与直接取得 Shell 的影响不同。

JTAG 和 SWD 则可能连接处理器调试架构。在目标芯片允许访问时，调试器可以暂停运行、观察寄存器、读取内存或编程 Flash。OpenOCD 文档明确区分了 JTAG 的测试与调试用途，以及 SWD 的调试用途；工具识别到接口，并不证明芯片已经授权所有访问。[OpenOCD 调试传输文档](https://openocd.org/doc-release/html/Debug-Adapter-Configuration.html#Transport-Configuration)

还应单独识别 ROM 下载模式。它可能绕过应用直接执行芯片内置下载程序，支持的读取、写入、解密或执行能力由芯片型号、修订版和安全配置共同决定。把这类模式与应用串口混为一谈，会漏掉重启期间的入口。

## 调试能力怎样绕过应用防线

下面是一条条件化的攻击链：设备在量产状态仍允许调试读取；敏感进程把云端令牌解密到普通内存；调试端口可以读到该地址空间；令牌还能被外部客户端复用。此时，应用层的登录校验和静态存储加密都没有阻止令牌被提取。

这条链依赖四个条件，缺一项，结果就可能改变。只有日志输出时，攻击者未必能读取任意地址；调试只能访问非安全区时，安全区密钥未必可读；私钥不可导出时，攻击者仍可能尝试让已失陷应用代为签名；云端若限制令牌的受众、权限和有效期，单次泄露的影响又会缩小。

因此，审计结论应记录“读到了什么、改变了什么、以什么身份继续访问”，而不是只写“发现四个焊盘”。

## 量产配置比接口名称更能解释风险

ESP-IDF v5.3.4 的 ESP32 安全文档把调试接口、UART 下载模式、安全启动与 Flash 加密放在同一套量产安全设计中，并区分 ESP32 ECO3 前后的实现。这是一个具体的平台范例，不能直接推广到所有 ESP32 系列芯片。[ESP32 安全配置说明](https://docs.espressif.com/projects/esp-idf/en/v5.3.4/esp32/security/security.html#debug-interfaces)

公开研究也提供了反例。Tarlogic 的一篇智能门锁硬件分析记录了 UART 和 SWD 调试总线被禁用的情况。这个结果说明“设备能拆开”与“调试访问成功”之间存在真正的控制边界；后续研究需要转向存储总线、无线协议或其他可达入口。[Tarlogic 智能门锁硬件分析](https://www.tarlogic.com/blog/hardware-vulnerabilities-smart-locks/)

## 用能力变化记录发现，而不是用接口名评级

下面是可用于样机审计的判定表，结论需要由实际观察填充：

| 观察 | 已经证明的能力 | 仍需核对的边界 |
| --- | --- | --- |
| 启动日志可读 | 被动获取日志中的信息 | 是否存在秘密，是否接受输入 |
| 进入维护控制台 | 调用控制台开放的功能 | 是否认证，能否修改启动与网络配置 |
| 调试器可读 RAM | 读取被允许地址空间的运行数据 | 是否包含明文秘密，安全区域是否隔离 |
| 调试器可改程序计数器 | 改变受控执行上下文 | 能否访问受保护外设或调用密钥服务 |
| 下载模式可写 Flash | 修改可写持久化区域 | 启动验签是否拒绝被修改镜像 |

表中的能力不构成逐级包含关系。例如，允许量产烧录的下载器可以只写不读；能读非安全 RAM 的调试器，未必能操作安全世界中的密钥。

还应把接触本机与影响其他设备分开。若某个令牌只能访问本机遥测数据，影响范围与全局维修密码不同。可以构造一条权限变化记录：“物理接触 → 非安全内存可读 → 取得本机测试令牌 → 可查询本机资源，其他设备访问被拒绝”。这比直接标记“设备完全失陷”更方便审查，也能明确修复哪一步最有效。

## 把受控读取落到具体地址与权限

从实际调试会话记录设备状态、访问地址、对应内存区域、读取结果与工具错误。普通 RAM 可读、受保护区域被拒绝、能否改写执行状态应分别保留证据，不用一份预填成功结果的记录代替观察。

指定普通内存可读，不支持直接推断“获得 Shell”或“提取受保护密钥”。继续判断影响时，应明确普通内存中是否存在可复用的会话秘密，以及这些秘密允许哪些操作。

同样的测试需要在复位、下载和维修状态重做。若正常启动拒绝调试，而复位后短暂开放访问，就要继续核对该窗口中是否已经存在敏感数据或可改变安全配置的能力。不能把某一状态的测试结果推广到整个设备生命周期。

## 维修通道应授予有限能力

如果产品必须保留维修调试，授权应绑定具体设备、具体能力和有效时间。读取诊断日志与读取完整内存不应默认属于同一级权限；进入维修状态也不应让设备继续持有完整生产身份。

一种可评估的设计是：维修授权由独立服务签发，设备验证授权后仅开放必要接口；进入高权限维修前清除业务会话，退出时恢复量产配置，并留下状态变化记录。这会增加售后服务的离线处理难度，需要明确断网维修时如何验证授权，避免最终又放回一个全设备通用口令。

永久关闭接口可以减少旁路，但也可能失去故障恢复能力。是否烧录不可逆安全位，需要结合芯片手册、升级与返修方案决定，不能把一次实验板验证当作量产方案。

## 怎样验证控制确实发生在硬件边界

验证对象应是量产样机及其实际安全配置，同时覆盖正常启动、复位、下载、恢复和维修状态。对每种状态分别检查接口发现、内存读取、Flash 编程和代码执行能力，保留失败原因；“工具连接失败”也可能只是时序或接线问题。

日志评估使用人工植入的测试秘密，观察它们是否进入启动输出和崩溃记录。调试权限评估则使用专门的测试地址与标记，证明允许读取的区域和禁止访问的区域。若能提取设备凭据，再在隔离的测试租户中验证其实际授权，避免把本机读取能力误报成全平台控制。
