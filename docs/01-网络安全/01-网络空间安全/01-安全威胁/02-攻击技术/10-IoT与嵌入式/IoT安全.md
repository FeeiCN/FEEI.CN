从真实固件和设备开始研究：先识别镜像、进程与通信入口，再验证输入怎样改变设备或账号的权限。下面的 12 篇文章分别给出工具、材料来源、操作顺序与结果判据；产品相关请求从实际 App、设备日志和发布包取得。

## 先确认手里的材料与权限

IoT 研究会跨越硬件、固件、无线和云端。先记录设备型号、硬件修订、固件与 App 版本，再选择能实际完成的操作。下面三种起点需要的材料不同：

| 已有条件 | 可以先完成的工作 | 继续深入所需材料 |
| --- | --- | --- |
| 只有厂商公开固件 | 解包、识别架构与组件、追踪配置和代码 | 运行环境、对应版本源码或实机请求 |
| 有自己的设备与普通用户账号 | 串口观察、App 抓包、两账号授权与换绑验证 | 对应连接器与电平、可重复的操作、设备恢复方法 |
| 有项目源码、签名产物或测试后台 | 构建匹配、签名与升级检查、Broker ACL、服务端日志对照 | 与量产一致的构建配置、设备身份和实际部署规则 |

普通用户不必先取得后台管理员权限。没有服务端日志时，用自己两台设备的回读、合法观察端和请求差异验证外部行为；结论需要后台证据才能成立时，再明确缺少的材料。获取设备标识、取得身份凭据和获准访问目标资源分别记录。

## 固件与工具准备 <!-- #lab-environment -->

软件分析以 Ubuntu 24.04 工作机为基准，macOS/Windows 可以使用 Ubuntu 虚拟机。UART 和 BLE 需要工作机实际能访问串口、蓝牙适配器；不能假定 WSL2 或虚拟机已完成硬件透传。先安装分析工具：

```bash
sudo apt update
sudo apt install curl gzip file squashfs-tools binutils ripgrep qemu-system-x86 nmap mosquitto-clients bluez adb unzip apache2-utils python3-venv git openssl
mkdir -p iot-research
cd iot-research
python3 -m venv .venv
source .venv/bin/activate
python -m pip install esptool==4.8.1 pyserial==3.5
```

Ghidra、Burp、Wireshark 和硬件采集设备按相应文章的官方入口安装。SPI 存储读取另装 `flashrom`，ESP32 JTAG 使用 ESP-IDF 配套的 Espressif OpenOCD；侧信道模型使用独立的上游兼容研究环境。`python` 指当前虚拟环境解释器，系统网络与二进制工具不依赖这个环境。

### 下载真实发布固件

固定使用 OpenWrt 24.10.5 的 x86-64 公开镜像作为分析样本，便于对照文件与构建信息；这是历史研究版本，不代表部署版本推荐。下载地址和摘要见[官方目录](https://downloads.openwrt.org/releases/24.10.5/targets/x86/64/)。

```bash
export FIRMWARE_BASE=https://downloads.openwrt.org/releases/24.10.5/targets/x86/64
curl -fLO "$FIRMWARE_BASE/openwrt-24.10.5-x86-64-generic-squashfs-rootfs.img.gz"
curl -fLO "$FIRMWARE_BASE/openwrt-24.10.5-x86-64-generic-squashfs-combined.img.gz"
curl -fLO "$FIRMWARE_BASE/openwrt-24.10.5-x86-64.manifest"
curl -fLO "$FIRMWARE_BASE/sha256sums"
shasum -a 256 openwrt-24.10.5-x86-64-generic-squashfs-rootfs.img.gz
shasum -a 256 openwrt-24.10.5-x86-64-generic-squashfs-combined.img.gz
rg 'generic-squashfs-(rootfs|combined)\.img\.gz' sha256sums
```

逐个比对完整摘要。哈希相符证明下载文件与该清单一致，来源认证还需独立可信的发布渠道与签名密钥。分析专有产品时，保存型号、硬件修订、固件版本、获取地址与哈希，不预设公开镜像包含现场账号秘密，也不把旧漏洞外推给此样本。

### 运行同一官方固件 <!-- #openwrt-qemu -->

```bash
gzip -dk openwrt-24.10.5-x86-64-generic-squashfs-combined.img.gz
```

此官方组合包在 gzip 数据后带有升级工具附加区；GNU gzip 解压时可能提示 `trailing garbage ignored` 并返回非零状态，但已经生成 `.img`。先确认压缩包摘要与官方清单一致，再检查解压文件；其他解压错误不能按这个提示忽略。原始 `.gz` 留给升级检查，QEMU 使用解出的磁盘镜像。

```bash
qemu-system-x86_64 -m 256 -nographic -snapshot \
  -drive file=openwrt-24.10.5-x86-64-generic-squashfs-combined.img,format=raw \
  -netdev user,id=net0,net=192.168.1.0/24,restrict=on,hostfwd=tcp:127.0.0.1:2222-192.168.1.1:22,hostfwd=tcp:127.0.0.1:8080-192.168.1.1:80 \
  -device e1000,netdev=net0
```

启动完成按回车进入控制台，运行 `passwd` 设置本次研究的 root 密码，再运行 `ubus call system board` 确认版本。在另一个终端访问 `http://127.0.0.1:8080/` 或 `ssh -p 2222 root@127.0.0.1`。端口只转发到本机；QEMU 用户网络限制与转发语法见[官方参数文档](https://www.qemu.org/docs/master/system/invocation.html)。

这里使用真实 Linux 固件的系统仿真，可用于进程、管理接口和升级检查；不模拟路由器射频、加密 eFuse、电池或物理调试保护。`-snapshot` 使磁盘修改在退出后丢弃，重启 QEMU 后要重新设置密码；不要在未导出证据时退出。控制台执行 `poweroff` 关机，必要时用 QEMU 的 `Ctrl+A`、`X` 退出。

连接失败时，先在固件控制台用 `ip addr` 核对 LAN 是否为 192.168.1.1，再用 `netstat -lnt` 检查 22/80 监听。8080 或 2222 被占用时，同时修改转发和后续客户端端口。命令与材料已按上游入口核对，本文未在实机或 QEMU 上宣称获得漏洞利用结果。

## 真实攻击案例

### Mirai 僵尸网络

Mirai 利用设备暴露的远程登录服务与可猜测凭据感染设备，再将其用于分布式拒绝服务。USENIX Security 2017 的原始研究分析了其在 2016 年的发展和影响，说明入口可达性、凭据管理与批量部署如何共同放大风险。[Understanding the Mirai Botnet](https://www.usenix.org/conference/usenixsecurity17/technical-sessions/presentation/antonakakis)

这类路径应分别检查服务是否可达、认证是否有效、凭据是否共用，以及登录后能执行什么。改掉默认口令可以切断对应凭据路径，但不能代替管理服务和固件漏洞修补。

### 摄像头劫持与隐私泄露

摄像头的媒体读取、设备管理与云存储可能使用不同授权路径。Bitdefender 在 2022 年公开的 Nooie 研究展示了消息服务认证缺失如何继续影响媒体上传目的地与录制数据访问，并记录了厂商随后确认修复。分析时应区分视频流访问、云数据读取与设备代码执行，不能由其中一项直接推出其他能力。[原始披露](https://www.bitdefender.com/en-gb/blog/labs/vulnerabilities-identified-in-nooie-baby-monitor)

## 固件

### 固件提取

固件可以来自厂商公开下载、升级缓存、设备文件系统或存储读取。选择路径取决于研究条件，并非必须先软件后硬件。应同时记录设备型号、固件版本、文件哈希和获取方式；读到镜像不等于获得其中秘密或执行权限。

#### 预留接口读取

JTAG/SWD 是调试接口，不因存在焊盘就构成后门。读取范围与可用操作取决于芯片访问控制、量产安全状态和调试授权；接口识别、普通内存读取、受保护区域读取与代码执行应分别验证。

##### JTag/SWD

Jlink/Xtag（GDBs/OpenOCD）插入Jtag->Jflash读取

#### UART/USART

UART 可能只输出日志，也可能连接登录控制台或 Bootloader。能否接受输入、是否要求认证、是否允许修改启动参数，需要逐项验证。下面的启动参数路径仅在可交互控制台允许改写配置、且启动策略未阻断相应变化时成立；它不是所有设备的通用取权方法。

- USB转TTL，连接主板UART口
- 使用串口工具连接，电气电平、波特率与帧格式按具体设备确认
- 上电，判断日志、交互输入与认证状态
  - 通过init启动sh。printenv、setenv bootargs init=/bin/sh、saveenv、getshell

#### 提权获得文件系统权限

**当正常调试接口受限时，设备自身的提权漏洞或后门同样可以作为突破口。** 利用已知漏洞或预置后门获得完整 Shell 后，即可访问文件系统并提取固件。

#### 从存储芯片读取固件

在线或拆焊读取 Flash 可以取得存储副本，但不自动绕过加密。副本能否分析取决于分区、加密方式、密钥保护与设备状态。ESP-IDF 的 ESP32 Flash Encryption 文档给出了具体平台的片外存储保护范例，不能推广为所有芯片的同一实现。[官方文档](https://docs.espressif.com/projects/esp-idf/en/v5.3.4/esp32/security/flash-encryption.html)

##### 飞线Flash芯片在线读取固件

通过芯片夹连接到芯片的引脚，连接电脑，使用编程器即可读取保存固件。

##### 拆焊Flash芯片离线读取固件

将Flash芯片拆焊下来，通过烧录座编程器，离线读取保存固件。

拆焊STM32->插入烧录座->Jlink插入Jtag->JFlash读取。

#### 其它获取固件方式

**固件在流通环节中往往存在公开可获取的副本，软件手段有时比硬件手段更高效。** 官方渠道、第三方分享、OTA 更新抓包以及逆向配套软件都是低成本获取固件的路径。

- 官网下载
- 找售后客服或代理商要
- 三方网站共享的
- 中间人抓包获取更新固件时的远程链接
- 有些产品固件更新需要借助独立的软件，可逆向该软件获得固件。
- 逻辑分析仪
- 修改uboot启动脚本，删除密码、启动sh、挂在硬盘等方式获取高权限和文件
- 通过uboot的md命令读取内存，NOR Flash使用

## 网络协议攻击面

### MQTT 协议漏洞

MQTT 采用发布/订阅模型，部署安全需要连接认证、传输保护、主题授权与业务指令校验共同完成。Broker 的匿名访问设置与主题授权决定客户端能访问哪些消息；未授权的订阅或发布应追溯具体配置与实现缺陷。[MQTT 5.0 规范](https://docs.oasis-open.org/mqtt/mqtt/v5.0/os/mqtt-v5.0-os.html)

典型失效包括订阅越权导致数据泄露、发布越权导致控制消息被错误转发，以及消息积压或实现漏洞影响可用性。连接成功不代表拥有目标主题的发布权限，主题发布成功也不证明设备已经执行动作，需沿完整链路确认。

防御方向：

- 启用 TLS/SSL 加密传输层，避免明文传输
- 配置用户名/密码认证和 ACL 访问控制列表，限制每个客户端只能访问特定主题
- 将 MQTT Broker 部署在内网，避免直接暴露到公网

### CoAP 协议漏洞

CoAP 面向受限设备，RFC 7252 定义了请求/响应交互与安全模式；部署也可使用 OSCORE 保护消息对象。资源是否允许未认证读写、是否存在放大条件，需要结合配置与实现判断。使用 UDP 不能直接推出设备没有状态或缺少安全机制，详见[协议消息认证与授权](./06-IoT协议消息认证与授权.md)。[RFC 7252](https://www.rfc-editor.org/rfc/rfc7252.html)

### OTA 更新劫持

OTA 更新需要分别验证下载通道、发布身份、实际镜像、目标兼容性与版本策略。攻击者影响下载渠道后，仍需要跨越设备的安装与启动验证才能执行恶意镜像；签名正确的旧版本则需要另外检查安全版本与回滚政策。具体条件见[固件更新与回滚防护](./09-IoT固件更新与回滚防护.md)。

防御方向：

- 对更新包实施固件签名，设备验证签名后再执行更新
- 使用 TLS 加密更新传输通道，并严格校验服务端证书
- 实施安全启动（Secure Boot），确保只有经过签名的固件才能运行

## 云后端与移动 App 攻击面

设备、App 与云端共同维护身份、控制与数据权限。应沿具体接口检查账号是否拥有目标设备与动作的权限，以及临时凭据、消息队列和设备本地状态是否保持同一授权意图。需要检查的路径包括：

- **云 API 越权访问**：后端接口存在 IDOR（不安全的直接对象引用），攻击者通过遍历设备 ID 可以访问并控制其他用户的设备。
- **移动 App 逆向**：App 中硬编码的 API 密钥、云存储凭证、加密密钥可以通过反编译直接提取，进而横向移动攻击云端。
- **API 流量重放**：App 与云端通信的控制指令（开锁、关警报）被拦截后重放，在缺乏时效性校验的系统中直接生效。
- **云凭证泄露**：S3 Bucket 等云存储配置错误导致大量设备数据（固件镜像、用户数据、日志）公开可访问。

## 固件逆向

### 识别压缩算法

分析镜像时可以结合文件头、分区、字符串和熵分布判断后续路径。高熵区段可能来自压缩或加密，但不能单靠熵图区分两者；应结合具体工具版本、格式识别结果与程序逻辑验证。

历史版本可能帮助理解加密格式和升级流程，但解密程序可见不等于密钥可得。可以检查以下版本关系：

- 早期固件版本没有加密，解密程序随着某个过渡版本提供，过渡版本的固件未加密，找到这个版本提取解密程序来解密最新版本固件。
- 早期固件就开始加密，中间更改了加密方案，新解密程序随着某个过渡版本提供，过渡版本使用的还是老的加密方式，找到这个版本提取解密程序来解密最新固件。
- 早期固件就开始加密，中间更改了加密方案，没有过渡期间，后续的版本固件直接使用新加密方案。

这些情况是研究线索，不据此推断出现概率或能否完成解密，还需要核对密钥来源与实际可用性。

在确认解密程序、所需密钥与运行依赖都可获得后，可以评估仿真或受控执行；依赖安全外设或不可导出密钥的程序，未必能在 QEMU 中直接运行。固件提取与仿真结果的证据边界见[固件漏洞与嵌入式利用](./04-IoT固件漏洞与嵌入式利用.md)。

## IoT 防御困境

设备固件可能经过芯片厂商、方案商与品牌商多次集成，因此上游 SDK 修复不等于产品固件已更新，产品发布新包也不等于现场设备已安装。维护时需要核对实际构建、支持期限、可用更新与恢复路径。源码可见性会影响研究方法，但不能替代对运行版本、权限范围和修复结果的验证。
