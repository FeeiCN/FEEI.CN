# 事件与应急

先处置和保护证据，同时判断适用报告规则。技术团队的内部事故等级，不能直接替代不同监管规则的事件分级。

## 先找到对应规则

| 事件相关事实 | 阅读路径 | 特别核对 |
| --- | --- | --- |
| 境内网络运营者发生网络安全事件 | [国家网络安全事件报告管理办法](./网络安全事件报告管理办法.md) | 主体类别、事件等级、接报对象及分级指南 |
| 涉及人民银行业务领域 | [人民银行网络安全事件报告管理办法](../../04-支付与金融安全/人民银行网络安全事件报告管理办法.md) | 业务适用、独立分级、舆情触发和报告链路 |
| 涉及关基或重大威胁 | [关基保护条例](../02-关键信息基础设施/关键信息基础设施安全保护条例.md) | 保护工作部门、公安及专项义务 |
| 发生或可能发生个人信息风险 | [个人信息保护法](../../02-数据与隐私安全/个人信息保护法.md) | 部门通知与个人通知分别判断 |

具体时限以各明细页对应正式规则为准，本入口不再复制另一份可能失去同步的时限表。

## 同一起事件建立并行义务表

建议每条义务记录：依据、适用主体、事件条件、等级、起算事实、接报对象、截止时间、责任人、报告内容和提交结果。未知信息明确标记并持续补充，不因等待完整根因延误适用报送。

例如支付系统故障伴随个人信息泄露，应分别判断国家网络事件、人民银行事件、关基及个人信息通知义务。向某一个机关提交材料，不能自动关闭其他链路。

## 用一条时间线验证流程

演练从原始告警、故障或供应商通知开始，依次记录首次发现、事实发生、判级、升级、止损、每次报送、收悉、恢复与处置结束。不同规则的起算点应单独核定，不把最终审批时间作为统一开始时间。

验收至少覆盖负责人不可达、信息不完整、主报送渠道故障和事件升级四种情况。报告生成成功不等于已经提交；事后总结也不能只保留内部复盘而遗漏适用的外部报送。
