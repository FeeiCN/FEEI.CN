# Thorsten Ball：我如何与 Agents 协作

一个 Agent 修好了登录回跳，并跑过了预发测试。接下来它还可以检查哪个版本已经上线，等两小时再看错误率。但如果它想扩大灰度、切换功能开关或给客户发邮件，每个操作都需要交付系统把请求和实际授权对上。让 Agent 能看见真实的交付进度，才能给它更完整的任务。让发布系统独立控制写入，才能放心让它在无人盯着时继续工作。

Thorsten Ball 在 2026 年 10 月 25 日分享了 15 条使用研发 Agent 的经验，涉及模型选择、工具、验证、异步协作和代码评审。下面按一次研发任务的过程整理这些经验，并用假设的登录修复说明团队接入发布系统时需要哪些控制。原文是 Ball 当时的个人实践，案例中的权限与验收设计是本站的应用示例。[How I work with Agents](https://x.com/thorstenball/status/2114386050638336082) · [本站整理记录 #782](https://github.com/FeeiCN/FEEI.CN/issues/782)

## 把结果和边界交代清楚

**优先试用能力更强的新模型。** Ball 看重的是验证和返工的代价。即使低价模型大多数时候能答对，审查者也很难提前知道哪些结果需要重做。团队可以让候选模型处理同一组代表性任务，记录首次验收通过率、返工轮数、评审用时和总费用，再决定哪些任务值得用更强的模型。模型更新后，用当前任务重新比较。

**描述做成后的样子。** 登录任务可以写成“从设置页发起登录，成功后回到设置页，并用测试证明外部跳转地址会被拒绝”。如果还没查清故障，就把路由和会话字段怎么改留给 Agent 定位。允许改动的代码范围、兼容要求以及是否允许部署，应在开始时定下来。优化性能也一样，先定负载、基准和必须保持的行为，再让 Agent 选实现。

**让 Agent 做工具，供人比较方案。** 页面布局有几种候选时，Ball 会让 Agent 做一个小页面，把候选方案摆在一起供人切换和比较。排查性能时也能这样做，让 Agent 列出几种可能原因，用同一负载分别测量数据库、网络和渲染耗时，记下哪些测量结果排除了哪些解释。下一轮讨论可以从这些结果开始。

## 让 Agent 接触真实的交付过程

**让交付的各个阶段可观察。** 单元测试通过后，Agent 仍需要知道预发是否跑完完整登录流程、部署对应哪个提交、线上观察的是哪个版本。提供这些证据，它就能指出哪一步完成、哪一步还缺记录。日志只返回任务所需的字段和时间窗，并附环境与版本，避免把客户数据、凭证或无关业务记录交给模型。

**为交付流程提供专用工具。** Ball 的团队给 Agent 提供了故障报告、系统健康、功能开关和客户邮件等工具。接入自己的系统时，可以分别提供读取发布状态、准备发布申请和执行发布的能力。以扩大灰度为例，发布服务应当在执行时核对发起身份、目标环境、制品版本和获准的灰度范围，并留下结果。客户邮件与功能开关由相应服务核对接收对象或变更范围。不可信的工单、日志和工具输出都可能进入上下文，执行服务应当只认自己的授权记录。工具如何约束实际副作用，见 [Agent 与工具调用安全](./Agent与工具调用安全.md)。

**给每个任务独立的运行环境。** Ball 偏好远程机器，因为多个 Agent 在同一台开发机上跑端到端测试，容易争抢端口、数据库和浏览器实例。团队可以用独立工作区、容器或按任务启动的远程环境解决资源冲突。依赖通过项目规定的来源安装，测试使用隔离数据，任务结束后回收环境。环境如何划定文件、进程和工具权限，见 [Harness 工程](../../../04-软件工程/01-人工智能/02-Agent与工具工程/Harness工程.md)。

## 用证据验收，把精力花在影响大的改动上

**要求别人可以复核的证据。** Ball 常要端到端演示、视频和前后对比。对登录修复，可以要求在旧版本复现错误跳转，在候选版本用相同步骤确认行为，并记录执行命令、环境、版本和结果。视频能展示当时看见的行为，回归测试可以让评审者重跑。“构建通过”证明制品能构建，验证登录回跳仍需要实际走一遍目标流程。常见的证据误用可以写入 `AGENTS.md`，让后续任务知道该交什么。

**验证仓库知识有没有被使用。** 仓库里的 `AGENTS.md`、Skill、脚本或文档写得再清楚，也要看 Agent 在实际任务中能否找到并照做。选几个代表性任务，用相同模型、仓库快照、工具与验收标准启动独立会话，只改变待验证的指导材料。不在任务描述里提示答案，记录各组是否找到正确入口、是否执行了必要验证、结果是否改善。少量试跑适合发现入口难找或规则写得含糊，调整通用规则前应覆盖更多代表性任务。权限限制在各组都由执行环境强制。

**用可维护性判断代码质量。** Ball 对“Agent 会不断堆积烂代码”的担忧没有早先那么强。他会问能不能从架构图上说清主要调用关系、有没有跑过端到端测试、一个月后能不能改动这段代码。偶尔出现的命名不整齐或少量重复，可以按实际维护成本判断。如果重复的是权限判断，两处实现以后可能演变成不同规则，值得当场处理。

**优先细审影响范围大的代码。** Ball 会细看关键文件和数据库迁移。团队可以同样把评审时间优先给鉴权、发布、公共接口和难以回滚的变更，核对兼容性、错误处理与恢复方法。对范围明确、容易撤回的改动，可以先看调用关系和运行证据，再检查关键差异。现有合并门槛与必过检查仍由仓库执行。通用的任务契约与代码验收方法见 [AI Coding](../../../04-软件工程/01-人工智能/03-AI应用实践/AI编程.md)。

## 让 Agent 异步工作，在需要决定时交回给人

**把能独立验收的工作一次交付。** 可以把复现、修复、验证和整理差异作为一项任务，让 Agent 连续推进，在需要确认灰度范围时交给负责人。交接时附上候选提交、预发结果和实际待决事项。团队可记录从发出任务到拿到可评审改动的时间，以及中途需要几次人工介入，用它们判断异步是否划算。方向未定的任务适合先约一个小的中间结果。

**用定时或事件唤醒完成后续检查。** Ball 举的例子包括两小时后看日志、上线后通知和每天定时检查。发布后观察错误率时，指定目标版本、环境、观察窗口、异常接收人和结束条件。等待、已观测、已处置应有各自的状态。若排队中的任务可能触发写入，执行服务要在提交业务操作时核对授权是否仍然有效。相关机制见 [Agent 权限撤销与异步执行](./Agent权限撤销与异步执行一致性.md)。

**让工具压缩上下文，一条线程跟一个任务。** Ball 不再手工盯上下文长度。任务跨越较多轮次时，可以让工具处理压缩，在任务记录里保留当前差异、已确认决定、最近一次验证和待办。恢复后先对照仓库与测试记录。摘要可以帮助续上工作，实际执行权限仍由系统根据当前任务和授权记录判断。

**把线程连到团队已有的决策记录。** Ball 提到 Amp 可以将线程关联到 Git 提交，后来的人能沿着变更找到当时试过什么、为什么采用当前方案。其他团队可以在 PR 中保留可访问的讨论链接、被排除的方案和验证结果。长期可用的决策可以提炼到项目文档，线程原件按受众与留存要求管理。

**由负责人写需要对人负责的内容。** Ball 会把调试步骤、部分文档和事件记录等按事实整理的工作交给 Agent。面向客户的解释、给同事的反馈、需要表达立场或作出承诺的文字，应由负责人决定内容和措辞。Agent 可以整理已核实的时间线或准备草稿，发送前由负责人核对对象、事实和承诺。
