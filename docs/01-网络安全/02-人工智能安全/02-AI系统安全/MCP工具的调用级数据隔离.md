# 外部 OCR 可以收发票，为什么还要隔离 MCP 工具的每次调用？

假设一家公司的文档助手有两项业务。人力部门让它在内网读取工资表，财务部门让它把发票交给获准使用的外部 OCR 服务识别。两项业务可以使用同一个 MCP 工具，但公司只允许外部服务接收发票。这个例子用来说明权限边界，并非一起已披露的安全事件。

财务人员发起第二次调用时，只选了一张发票。网关也可以确认这次请求发往正确的 OCR 服务。还有一件事要核对：**负责发送发票的工具进程，有没有可能同时读到上一次调用的工资表？** 如果两次调用共用一个进程，且工资数据仍留在进程可读的状态里，财务人员选中的文件和工具实际能接触的数据就是两个不同的范围。

## 白名单管连接，进程决定工具能看到什么

Aun 等人在 2026 年 11 月 4 日发布的预印本里，用 OCR 场景研究了这条边界。论文假设工具代码不可信，宿主策略仍由可信组件执行。在这项假设下，工具签名可以验证发布者身份和制品完整性，出站白名单可以限制连接去向。要守住工资表的边界，宿主还需要控制每次调用实际能接触的数据。[《Signed, Sealed, Leaked》v1](https://arxiv.org/abs/2611.06585v1) · [Sigstore 文档](https://docs.sigstore.dev/about/overview/)

论文测试了 MCPGuard-Dynamic 的 `825fdc0a` 版本。在这版公开源码里，代理启动一次工具子进程，后续调用继续向同一个子进程发送消息。逐调用的网络策略也作用在这个进程上。策略可以随调用切换，但切换策略时，进程里已有的状态仍然存在。源码能确认的是进程复用和策略的作用范围。[MCPGuard-Dynamic 固定版本源码](https://github.com/facebook/mcpguard-dynamic/blob/825fdc0a372b639b235e369880580a8093e76c71/proxy/proxy_base.py)

MCP `2026-07-28` 版规范要求请求携带处理所需的上下文，同时允许多个请求通过同一个常驻的标准输入输出进程传递。评审时，即使接口符合无状态规范，也要单独检查宿主是否隔离了调用之间的进程状态。[MCP 规范的无状态条款](https://modelcontextprotocol.io/specification/2026-07-28/basic/index#statelessness)

## 换一个干净进程，再只给它这次能外发的文件

先把两次调用的执行环境分开。内网进程读取工资表，负责连接外部 OCR 的进程从干净状态启动。这个做法成立的前提是，外发进程也无法通过共享目录、缓存或其他持久状态读回工资表。否则，换了进程，数据仍在它能访问的范围内。

再看一种常见的请求。用户一次选中多个文件，请助手整理资料，其中有工资表和发票。即使这次启动了干净进程，只要把两份文件都交给负责外发的工具，它依然能读到工资表。宿主应该在工具收到数据之前完成筛选，让连接外部 OCR 的执行环境只拿到获准外发的发票，让工资表留在只能走内网处理的环境里。

| 业务场景 | 评审时要核对的边界 |
| --- | --- |
| 上一次处理工资表，这一次识别发票 | 外发进程是否从干净状态启动，是否还能读到之前留下的缓存或文件？ |
| 同一次请求选中工资表和发票 | 宿主是否在交给外发工具之前筛掉了工资表，工具还能否通过共享存储读取原文件？ |

论文把这项要求称为 `invocation purity`。放在这个例子里，外部 OCR 收到的请求只能依赖本次允许它接收的数据，以及同样获准用于这个目的地的显式状态。确实需要跨调用保存状态时，例如记录同一批发票的识别进度，宿主可以按业务和数据权限保存状态，再把对应部分交给下一次调用。这样可以保留处理进度，同时让工资表与外发环境各自保持清楚的访问边界。[论文第 II-C 节与第 IV 节](https://arxiv.org/html/2611.06585v1#S2.SS3)

## 论文结果能支持什么判断

作者的 Germline Execution 原型从不含用户数据的基础进程创建临时副本，每个副本只接收对应目的地获准使用的输入。作者报告，在该原型的 153 次攻击测试运行中，未检测到未授权的测试标记外泄。v1 附录称原型、测试环境和固定结果文件将随会议版本发布。这里对照了预印本和基线源码，效果数字沿用作者报告，尚无本文的独立复现结果。[论文第 VII 节](https://arxiv.org/html/2611.06585v1#S7) · [附录 D](https://arxiv.org/html/2611.06585v1#A4)

对于要接入外部 OCR 的团队，可以直接从数据访问范围验收设计。用合成的发票和工资表确认正常发票能被识别，再分别检查外发执行环境能否访问上一次留下的合成工资表，或同一次请求中未获准外发的合成工资表。向外部服务开放连接后，仍要能在宿主侧回答：这一次负责发送发票的进程，实际拿到了哪些文件和历史状态？

关于 Agent 运行期间的工具授权、参数审批和资源侧校验，参见 [Agent 与工具调用安全](./Agent与工具调用安全.md)。原始研究讨论见 [Issue #805](https://github.com/FeeiCN/FEEI.CN/issues/805)。
