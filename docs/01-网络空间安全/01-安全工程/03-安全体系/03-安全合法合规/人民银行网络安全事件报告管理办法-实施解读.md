# 央行4号令实施解读

> 对应原文：[中国人民银行业务领域网络安全事件报告管理办法](./人民银行网络安全事件报告管理办法.md)  
> 中国人民银行令〔2025〕第4号，2025年8月1日起施行。官方原文：https://xining.pbc.gov.cn/tiaofasi/144941/144957/5729954/index.html

## 30 秒理解

这部办法解决的是一个非常具体的问题：**金融机构发生网络安全事件后，如何判断事件等级、向谁报告、多久报告、报告什么、后续如何复盘和留证。**

对安全负责人而言，核心不是背条文，而是把下面这条链路真正跑通：

```text
监测发现
  ↓
立即启动应急处置
  ↓
按统一规则判断事件等级
  ↓
确定报告对象
  ↓
在法定时限内发出简报/正式报告
  ↓
持续进展报告
  ↓
事后调查、责任认定、整改
  ↓
台账留存与复盘
```

## 最关键的时间要求

| 场景 | 必须完成的动作 | 时间要求 |
| --- | --- | --- |
| 较大及以上事件 | 事发简要报告 | **1小时内** |
| 较大及以上事件 | 事发报告 | **24小时内** |
| 重大及以上事件 | 事中进展报告 | **至少每2小时一次**，直至处置结束；重要变化立即报告 |
| 所有需报告事件处置结束后 | 事后调查总结报告 | **10个工作日内** |
| 10个工作日内无法形成完整总结 | 先报初步报告并承诺最终日期 | 承诺日期原则上不晚于处置结束后**40个工作日** |
| 网络安全事件台账 | 保存事件和报告全过程 | **至少3年** |
| 事件分级标准 | 定期评估并视情更新 | **每年至少评估一次** |

如果事件尚未达到较大等级，但已经进入社交媒体、搜索引擎或新闻网站热点榜并引发较大舆情，也要按较大及以上事件的1小时/24小时要求报告。

## 事件等级怎么判断

办法要求机构建立自己的分级标准，将事件分为：

- 特别重大；
- 重大；
- 较大；
- 一般。

分级时至少看四类影响：

1. **业务中断程度**：是否影响主要功能、持续多久、影响几个省级区域，是否处于业务高峰。
2. **用户影响规模**：实际影响多少自然人、法人和其他组织。
3. **数据影响**：是否涉及核心数据、重要数据、敏感个人信息、征信信息、财产信息等泄露、篡改或破坏。
4. **攻击和社会影响**：例如勒索攻击、舆情扩大、公安/网信部门已有明确等级判断等。

一个非常重要的兜底规则：**对照标准仍无法准确确定等级时，至少按“较大事件”处理。**

## 安全要求实施矩阵

| 安全要求 | 实际要做什么 | 推荐实施方式 | 做到什么程度才算基本落地 | 关键条款 |
| --- | --- | --- | --- | --- |
| 建立分级标准 | 将监管阈值翻译成本机构事件分级规则 | 将系统中断、用户规模、数据类型/数量、攻击类型等配置成规则表或自动判级逻辑 | 每类主要系统均有可执行分级标准；**每年至少评估一次**，变更有主管领导批准 | 第6条 |
| 事件发现 | 尽快发现网络、系统、数据异常 | SOC/SIEM、APM、数据安全监测、告警聚合、7×24值守 | 关键事件能够在分钟级进入应急流程，而不是靠业务投诉后才发现 | 第13条 |
| 应急与报告分工 | 处置和报告同时推进，避免互相等待 | 预案中明确技术处置、监管联络、法务、舆情、业务恢复角色 | 发生事件后能立即知道谁判级、谁审批、谁向监管报告；报告不得拖慢恢复和取证 | 第13条 |
| 报告对象判断 | 明确应向总行还是属地央行分支机构报告 | 建立机构类型和报告对象映射表，维护监管联系人 | 值班人员无需临时查法规即可找到正确报告对象和备份联系人 | 第14条 |
| 1小时简报 | 在信息尚不完整时先完成最低必要报告 | 建立固定模板并自动带出系统、等级、时间、联系人等字段 | 较大以上事件从确认触发到监管收悉控制在1小时内，并保留发送和收悉证据 | 第15、18、19条 |
| 24小时正式报告 | 补充影响范围、处置措施和攻击研判 | 事件平台自动汇总时间线、影响数据和处置记录 | 24小时内可形成完整可签发版本，不依赖临时手工拼材料 | 第15、19条 |
| 持续报告 | 重大以上事件持续向监管同步进展 | 自动定时提醒，每2小时生成进展报告草稿 | 重大以上事件至少每2小时更新；等级上调、阶段性进展、新问题立即报告 | 第16条 |
| 个人信息事件 | 同步处理通知个人和减轻危害义务 | 将个保事件处置纳入统一应急流程 | 总结报告能够说明补救措施、通知个人情况和减轻危害措施 | 第20条 |
| 责任认定 | 事件后不仅找技术原因，还要形成责任处理结论 | RCA同时覆盖技术根因、流程失效和管理责任 | 较大以上事件的总结报告中有责任认定和处理情况，且依据内部制度而非临时决定 | 第21、22条 |
| 事后总结 | 形成完整时间线、损失、根因、改进计划 | 统一RCA模板，重大事件组织跨部门复盘 | 10个工作日内提交；问题有Owner、期限、关闭证据 | 第17、19条 |
| 风险通报响应 | 收到央行风险提示后立即核查 | 建立监管通知工单和快速核查机制 | 风险属实立即补救并按事件规则报告；不属实或未构成事件也按要求反馈 | 第24条 |
| 台账 | 保留全部事件及监管报告历史 | 统一事件管理平台或不可随意修改的台账 | 事发、判级、报告时间、监管联系人、报告内容完整可追溯，**至少保存3年** | 第25条 |

## 建议把“1小时”拆成内部更短的SLA

监管要求是1小时，不代表内部流程可以用满1小时。更稳妥的做法是预留审批、传输和确认收悉时间，例如：

```text
T+0      发现/确认事件
T+10min  初步影响确认，启动判级
T+20min  判断是否达到较大以上或舆情触发
T+30min  形成简报草稿
T+40min  完成内部审批
T+50min  发出并确认监管收悉
T+60min  监管法定时限上限
```

这不是法规规定的固定内部分钟数，而是为了确保法定1小时要求可稳定达到的工程化设计。

## 分级落地不要靠人工背阈值

推荐把监管阈值配置成事件系统规则。例如：

```text
事件输入：
- 业务系统/网络
- 是否业务高峰
- 中断区域
- 中断时长
- 失败业务占比
- 影响自然人数/机构数
- 数据类型及泄露规模
- 是否勒索攻击
- 是否被监管部门明确分级

系统输出：
- 建议等级
- 触发依据
- 需报告监管机构
- 下一个法定时间点
- 所需报告模板
```

人工可以提高等级，但不应因为判断不清而降低等级；无法准确判断时按至少较大处理。

## CISO 自查清单

- [ ] 是否有正式事件分级制度，并在过去12个月内评估过？
- [ ] 是否把业务高峰/非高峰、用户影响量、数据类型和数量写进判级规则？
- [ ] SOC值班人员是否能在5分钟内找到当前版本分级表？
- [ ] 是否明确每类机构/分支机构对应的监管报告对象和联系人？
- [ ] 是否有1小时简报、24小时事发报告、2小时进展报告和事后总结模板？
- [ ] 是否做过“发现事件到监管收悉”的完整计时演练？
- [ ] 报告与业务恢复、取证、用户通知、舆情处置能否并行推进？
- [ ] 重大以上事件是否有每2小时自动提醒机制？
- [ ] 较大以上事件是否强制进入责任认定和整改闭环？
- [ ] 网络安全事件台账是否至少保留3年并可快速检索？

## 验收标准

真正完成4号令落地，不是“写了一份应急预案”，而是随机给一个事件场景，值班人员能够在很短时间内完成以下动作：

1. 判断是否属于央行业务领域；
2. 根据客观数据给出事件等级和依据；
3. 找到正确监管报告对象；
4. 自动计算1小时、24小时、2小时、10个工作日等关键时点；
5. 生成合格报告；
6. 证明监管已经收悉；
7. 在事后用台账还原整个处置和报告过程。

能够稳定重复完成这七件事，才算把法规要求真正变成了安全能力。
