# 中国人民银行业务领域网络安全事件报告管理办法

本文用于组织落实和检查央行4号令：**明确安全要求，选择实施方式，确定完成标准，用真实证据验证执行结果。**

[法规概览](#overview) · [安全要求与实施](#requirements) · [检查与验收](#assurance) · [Reference · 法规原文](#reference)

## 法规概览 {#overview}

| 项目 | 内容 |
| --- | --- |
| 法规 | 《中国人民银行业务领域网络安全事件报告管理办法》，中国人民银行令〔2025〕第4号 |
| 生效日期 | 2025年8月1日 |
| 适用对象 | 金融机构以及经中国人民银行批准设立或者认定的其他机构，在中国境内发生的中国人民银行业务领域网络安全事件 |
| 主要内容 | 事件分级、监测与应急职责、报告对象、时限、内容、渠道、调查总结和台账 |
| 核对依据 | [人民银行公布文本](https://xining.pbc.gov.cn/tiaofasi/144941/144957/5729954/index.html)、[司法部收录文本](https://www.moj.gov.cn/pub/sfbgw/flfggz/flfggzdfzwgz/202511/t20251112_527888.html)；本页最近条文核对日期为2026年9月16日 |

本办法聚焦事件分级与报告，不能替代数据安全、关基保护、个人信息保护等其他合规要求。非央行业务领域事件不按本办法报告，仍须判断其他适用义务；涉及国家秘密的，按有关规定执行。依据：[第2—4条](#law-2)、[第31条](#law-31)。

下文中，**“法规要求”概括条文明示的义务；“实施方式”“完成标准”“验证问题”和证据样式，是落实与检查建议。** 法定阈值不可自行放宽，建议实现可以替换，但需要证明满足同一义务。本文不是官方检查标准，也不构成对任何机构已经合规或一定通过检查的认定。存在适用、起算或解释争议时，应结合事实由法务合规核实，必要时向主管机关确认。

## 安全要求与实施 {#requirements}

按四个工作主题组织实施。每项要求只在本节完整说明，后面的检查章节统一规定取样、测试和结论方法，不再复制另一份要求清单。

| 工作主题 | 建议交付成果 | 建议牵头与参与方 |
| --- | --- | --- |
| [范围与职责](#scope-and-roles) | 适用范围清单、报告义务映射、职责和授权安排 | 安全与法务合规牵头，业务、运维、监管联络参与 |
| [事件识别与分级](#identification-and-grading) | 分级规则、指标口径、监测联动、年度评估及必要协商记录 | 安全牵头，业务、运维、数据、隐私参与 |
| [报告与持续更新](#reporting) | 报送规则、渠道、四类报告内容准备、个人通知判断机制 | 监管联络与安全牵头，法务、业务、隐私、公关参与 |
| [调查与留存](#investigation-and-records) | 调查与责任处理机制、通报处理记录、事件台账及证据索引 | 安全牵头，业务、法务、人力、内审及档案管理参与 |

这些分工和成果名称可按机构调整。每项工作在内部明确负责人、完成日期、证据位置和复核人；不要把真实事件材料、监管联系方式或内部架构发布到公开博客。

### 范围与职责 {#scope-and-roles}

#### 确定适用范围和并行报告义务 {#scope}

**法规要求。** 根据机构身份、业务领域以及受影响的网络和数据判断本办法是否适用。国家有关部门和其他金融管理部门另有报告规定的，还应从其规定；涉及危害计算机信息系统等违法犯罪的网络安全事件，还应及时向公安机关报案。

**实施方式。** 从机构完整的业务和系统清单出发，映射央行业务领域、相关数据、责任部门及报告链路。对排除的业务和系统记录理由。为其他适用法规单独登记触发条件、分级规则、起算依据、对象、时限和渠道，避免把央行口径直接套给所有接报机关。

**完成标准。** 范围内外均有依据；同一事件涉及多项义务时，能分别分派任务并跟踪结果。完成央行报告不会自动关闭其他监管报告、公安报案和个人通知任务。

**验证问题。** `IR-04-01`：将完整业务、系统清单与适用范围清单核对，能否逐项解释纳入和排除依据？`IR-04-28`：指定一个攻击或数据泄露场景，能否列出每条适用报告链路及其依据，而不只给出一份联系人表？

**证据。** 业务和资产清单、适用性判断、法规版本与报告义务映射、任务责任记录。只抽几个已知核心系统或只说“这些系统归央行管”，不能证明范围完整。

**依据。** [第2—4条](#law-2)。并行义务还应核对适用的[《国家网络安全事件报告管理办法》](https://www.cac.gov.cn/2025-09/15/c_1759583017717009.htm)、[关基保护条例](./关键信息基础设施安全保护条例.md)和[个人信息保护法](./个人信息保护法.md)。本页不代替这些法规的独立适用判断。

#### 明确处置职责、报送授权和报告对象 {#roles}

**法规要求。** 明确应急处置与报告的职责分工；发生网络安全事件立即启动应急预案、采取补救措施，报告工作不得迟滞业务恢复、存证溯源、用户解释和舆情应对。按机构类型向正确的人民银行机构报告。

| 机构或场景 | 人民银行报告路径 |
| --- | --- |
| 国家开发银行、政策性银行、国有商业银行、中国邮政储蓄银行、股份制商业银行、属于系统重要性金融机构的城市商业银行、系统重要性非银行支付机构、经营个人征信业务的征信机构 | 向中国人民银行报告 |
| 上一行所列机构的分支机构 | 向住所地中国人民银行分支机构报告 |
| 人民银行所属单位及其管理的金融基础设施运营机构 | 向中国人民银行报告 |
| 其他金融从业机构或其分支机构 | 向住所地中国人民银行分支机构报告 |
| 证券、期货、基金机构 | 在保障报告时效性前提下，经中国证监会派出机构转通报同级中国人民银行分支机构 |

**实施方式。** 在预案中落实判级、技术处置、报送、授权、隐私和舆情职责，维护可用联系人与渠道。建议设置主备人员和紧急授权，使主负责人不可达时仍可按合法授权推进，避免等待逐级审批。人民银行系统内部的逐级上报职责，不应混作企业自身的报送任务。

**完成标准。** 执行人员可定位当前机构的正确报告对象，并知道自己可执行的动作和授权边界；处置与报告可并行。备用方案应形成可执行授权，不能靠临时越权解决。

**验证问题。** `IR-04-07`：抽取不同班次人员，是否能按预案完成本人动作和交接？`IR-04-08`：指定总部或分支机构场景，是否能找到正确对象和可用渠道？`IR-04-11`：模拟主审批人不可达，报告能否依既有授权继续推进？三个问题分别判定。

**证据。** 生效预案、职责与授权记录、联系人维护记录、实际交接或测试记录。单有组织图、领导私人通讯录或“领导通常会接电话”的说明不够。

**依据。** [第13条](#law-13)、[第14条](#law-14)。主备安排、查找耗时及联系人验证周期属于实施建议，具体内部标准按[检查规则](#test-rules)登记。

### 事件识别与分级 {#identification-and-grading}

#### 覆盖事件来源，验证监测与研判联动 {#detection}

**法规要求。** 健全网络安全风险监测预警体系，提升第一时间发现和报告事件的技术能力。事件原因包括人为原因、网络攻击、漏洞隐患、软硬件缺陷或故障、不可抗力等；发生或者可能发生个人信息泄露、篡改、丢失，属于第十条规定的分级情形。

**实施方式。** 联通安全告警、生产故障、业务异常、数据异常、用户投诉和外部通报。收到线索后核实影响并进入适用的分级程序。安全、稳定性、数据和隐私团队可以使用不同平台，但须能关联事实、判级和报告任务。

**完成标准。** 不因“没有攻击”排除符合定义的故障事件，不以等待最终泄露取证为由搁置已有可信风险线索。误报或风险被排除的，保留核查依据；不能把任何告警无差别认定为较大事件。已有事件对照标准仍无法准确判级时，按下一项的兜底规则处理。

**验证问题。** `IR-04-06`：从告警、故障和投诉来源反查，是否都有可解释的研判结果？`IR-04-26`：纯发布故障导致支付业务中断，是否进入适用的4号令判级？`IR-04-27`：有效凭证暴露且可访问含个人信息的数据库，尚不能确认下载情况时，是否及时研判并记录依据，而非等待确认泄露才处理？

**证据。** 原始线索、首次发现时间、核查过程、排除理由、事件记录与报送任务的关联。监测平台截图本身不能证明规则启用和处置有效；投诉先于告警也不自动证明违法，应核查监测覆盖和实际响应。

**依据。** [第3条](#law-3)、[第10条](#law-10)、[第13条](#law-13)。

#### 建立完整分级规则并持续维护 {#grading-rules}

**法规要求。** 在制度或操作规程中明确特别重大、重大、较大、一般四级标准，每年组织评估、视情更新；更新须报主管网络安全的领导班子成员批准。针对指定业务考虑高峰和非高峰的差异，结合业务领域数据安全规定制定数据事件标准。涉及与央行管理的金融基础设施业务交互功能异常的标准，还须征求运营机构意见并协商一致。

下列条件按适用前提分别判断，**任一命中即达到至少相应等级，同时命中取最高等级**。“以上”含本数。各表为同一套规则的不同维度，不是综合打分表。

**用户影响条件。** 前提为提供金融服务的央行业务领域网络，主要功能中断、超时报错等导致业务无法正常开展，经合理测算或估算达到实际影响规模。不得直接用注册用户数代替实际影响人数。

| 最低等级 | 实际影响自然人 | 实际影响法人和其他组织 |
| --- | --- | --- |
| 一般 | 1万个以上 | 1000个以上 |
| 较大 | 10万个以上 | 5000个以上 |
| 重大 | 100万个以上 | 10万个以上 |
| 特别重大 | 1000万个以上 | 100万个以上 |

**数据及攻击条件。** 数量门槛对应“泄露”，不能不加区分地套用于所有篡改、丢失情形。数据类型须与本机构经核实的分类分级结果一致。

| 条件 | 最低等级 |
| --- | --- |
| 发生或者可能发生个人信息泄露、篡改、丢失 | 一般；仍须判断其他更高等级条件 |
| 央行业务领域数据遭篡改、破坏、泄露，导致社会危害 | 一般；仍须判断其他更高等级条件 |
| 泄露500条以上征信信息、财产信息，或者5万条以上个人信息 | 较大 |
| 泄露100万条以上敏感个人信息，或者1000万条以上个人信息 | 重大 |
| 泄露1000万条以上敏感个人信息，或者1亿条以上个人信息 | 特别重大 |
| 央行业务领域重要数据遭篡改、破坏、泄露 | 重大 |
| 央行业务领域核心数据遭篡改、破坏、泄露 | 特别重大 |
| 勒索恶意程序攻击已对央行业务领域网络或数据造成危害后果 | 较大 |

**业务中断条件。** 下表适用于金融基础设施、直接服务5000万个以上自然人，或者与货币存取款、支付交易、税款缴库、银行间市场交易密切相关的央行业务领域网络，且其主要功能在业务高峰时段发生相应范围的整体中断。

| 最低等级 | 两个以上省级行政区范围 | 单个省级行政区范围 |
| --- | --- | --- |
| 较大 | 整体中断15分钟以上 | 整体中断30分钟以上 |
| 重大 | 整体中断1.5小时以上 | 整体中断3小时以上 |
| 特别重大 | 整体中断3小时以上 | 整体中断6小时以上 |

一般事件还有独立条件：提供金融服务的央行业务领域网络主要功能单省整体中断30分钟以上；或者央行业务领域网络主要功能中断、超时报错等导致业务无法正常开展持续1小时以上。不得因不满足上表的特定网络或高峰前提而跳过这些条件；还应核对本机构其他适用分级标准。

网信部门、公安机关已明确的等级，以及人民银行或其上海总部、省级分行、计划单列市分行研判并书面告知的重大、特别重大等级，也须按第七至十条纳入判断。更高等级依据不能被另一维度较轻的结果抵消。

**实施方式。** 将适用前提、数据来源、计算公式、阈值、等级、条款和版本编成规则。规则可放在现有制度或工具中，无须另造一份文件。每年形成评估结论；未修改时仍记录评估，不强行产生新版本。涉及金融基础设施交互的，标识适用场景和协商状态。

**完成标准。** 规则覆盖全部适用触发条件和监管明确等级，业务及数据条件没有被错误简化；年度评估、实际更新审批和必要的协商一致均可证明。

**验证问题。** `IR-04-02`：独立选择阈值边界、高峰与非高峰、数据和监管定级场景，规则是否输出正确等级及依据？`IR-04-03`：检查期间各适用年度是否完成评估，实际更新是否有规定人员批准？`IR-04-29`：适用的金融基础设施交互标准是否有征求意见及协商一致证据？分别判断规则覆盖、评估、审批和协商，不能用场景答题正确代替后几项。

**证据。** 生效规则、法条映射、评估结论、更新记录及审批、往来协商记录。无单独规则表不必然不合格，只有四个等级名称则不足以证明可执行。

**依据。** [第6—12条](#law-6)、[第31条](#law-31)，并结合[央行数据安全管理办法](./人民银行数据安全管理办法.md)。

#### 取得判级数据并执行动态调整 {#grading-data}

**法规要求。** 对照标准综合判级；同时符合多个条件取最高等级，对照标准无法准确确定等级时至少分级为较大。灾害或信息基础设施故障使多个央行业务领域网络同时发生事件的，先分别判级，再取最高等级作为整体等级；事态达到更高级别标准时立即调整。

**实施方式。** 为各类网络明确指标负责人、时间窗口、地域划分、正常业务量基线、用户统计、数据类型及规模来源。允许有依据的合理测算或估算，记录方法、已知限制和后续更新；不必等所有数据精确到最终值才判级。

计算口径应遵守第31条：

| 指标 | 应采用的口径 |
| --- | --- |
| 主要功能 | 与用户身份认证或者业务交互相关的功能 |
| 业务高峰时段 | 按年度统计的分时平均业务量超过日平均业务量3%的时段，或者依据本机构制度列明的其他合理计算方式确定的时段 |
| 整体中断运行 | 某时段未处理和处理失败业务量之和，与正常情况下全部业务量的比例，经合理测算或估算超过70% |

整体中断的分母不是实际进入系统的请求量，也不能直接以某个接口的错误率替代。假设正常应处理10000笔，成功2000笔、未处理8000笔、失败0笔，则该比例为80%，不能因失败笔数为0得出“没有整体中断”。这是计算示例，实际还需满足相应网络、时段和地域前提。

**完成标准。** 判级结果能追到输入数据、方法、适用条款和时间。缺失数据明确标记，不以默认零值降级；等级变更保留前后版本、依据及报送动作。

**验证问题。** `IR-04-04`：指定系统和事件窗口，能否获得适用指标及可复核的估算方法？`IR-04-05`：用原始业务记录重新计算高峰、未处理量和整体中断比例，是否一致？`IR-04-15`：数据和隐私团队的影响判断是否进入同一事件的监管判级？`IR-04-30`：多网络受影响及后续升级时，是否分别判级、取最高级并及时调整？

**证据。** 查询或统计结果、计算脚本或人工步骤、基线来源、数据分类依据、判级及升级记录。人工统计可以接受，但临时口头估数、无法复核的总数或丢失旧等级均不能证明执行。

**依据。** [第6—12条](#law-6)、[第31条](#law-31)。15分钟取数等内部能力指标按[检查规则](#test-rules)单独验收。

### 报告与持续更新 {#reporting}

#### 明确报告触发条件和时限 {#reporting-deadlines}

**法规要求。** 报告及时、准确、完整，不得迟报、漏报或瞒报。不同义务按各自条件触发，持续报告与初次报告、技术处置并行。

| 触发条件 | 必须执行的报告义务 |
| --- | --- |
| 较大及以上网络安全事件 | 发生后1小时内报送事发简要报告，24小时内报送事发报告 |
| 尚未达到较大，但相关舆情出现进入社交媒体、搜索引擎或新闻网站热点榜等情形并引发较大舆情 | 按第15条同样执行1小时简报、24小时事发报告；该报告触发不等于事件等级自动变为较大 |
| 重大及以上事件处置期间 | 至少每隔2小时报送进展，直至处置结束；调高等级、取得阶段性进展、发现新问题等重要情况立即报告 |
| 一般事件，且未触发上述舆情情形 | 第15条第一款未统一规定其1小时、24小时首报要求；仍应履行适用的处置、[事后总结](#post-incident)、[台账](#records)及其他报告义务 |

**实施方式。** 建立事件及报告义务清单，为每条义务记录适用依据、到期点、执行人和提交结果。建议自动提醒、预先授权并预留内部缓冲；不得为等最终根因或层层审批而推迟依法报送。

**完成标准。** 每项适用时限均能独立验证；重大以上的进展报告覆盖整个适用期间，不能等24小时事发报告完成后才开始。检查首份进展、连续各次进展和处置结束前的尾段，不只计算两份中间报告的间隔。

起算判断须依据客观事件事实和适用监管口径。第15条没有规定可从内部审批或最终判级完成后重新计时。建议保留实际发生、客观达到相应条件、首次发现、初步判级、内部升级、各次报送及收悉的时间和依据。起点迟发现或不明确时，如实记录未知项并立即采取保守报送措施，不等待起点争议解决后再报告；由法务合规核实具体起算口径，不以发现时间当然替代发生时间。

**验证问题。** `IR-04-09`：检查期间适用首报的真实事件，每起简报是否满足1小时时限及起算依据？`IR-04-12`：相同事件的事发报告是否满足24小时时限？`IR-04-13`：重大以上事件是否覆盖全部进展报告期间，重要变化是否立即报告？`IR-04-14`：符合第15条第二款的舆情事件是否实际触发报送？逐项核验，不用“已经启动流程”替代“已经报送”。

**证据。** 原始时间依据、事件事实演进记录、报告版本、渠道提交记录、适用的收悉确认。内部工单关闭、报告已审批或事后补写时间线，单独都不足以证明按时报送。

**依据。** [第13条](#law-13)、[第15—17条](#law-15)。报送与收悉分别按[渠道要求](#report-content-and-channels)检查；真实事件和演练不混合计算通过率。

#### 准备报告内容，落实渠道和收悉要求 {#report-content-and-channels}

**法规要求。** 不同报告包含不同内容。下表列示字段依据，机构可以调整排版，但不能省略适用信息。

| 报告类型 | 应覆盖的内容 |
| --- | --- |
| 事发简要报告 | 初次确定的等级、事发时间、依据相关国家标准确定的事件分类、影响的央行业务领域网络及其保护等级、涉及的数据中心、报告机构和时间、报告人和联系方式 |
| 事发报告 | 简报内容，加影响范围和程度、已采取措施和效果；网络攻击事件增加分析研判情况 |
| 事中进展报告 | 简报内容，加最新等级、影响变化、处置进展、下一步措施；存在需要央行协调支持的事项时一并说明 |
| 事后调查总结 | 最终等级、处置历程、影响损失评估、技术或管理根因、经验教训、后续改进、报告机构和时间、报告人和联系方式、签发人；涉及个人信息或较大以上事件时，分别补入[个人信息事项](#personal-information)和[责任认定](#accountability) |

简报、事发报告和进展报告，可以使用电话、即时通信工具、电子邮件、传真或者人民银行指定系统。**采用邮件、传真时，应通过电话或即时通信确认已收悉。** 涉及工作秘密，不得通过互联网渠道报告。事后调查总结须书面报送并加盖本机构或承担报告职责内设部门公章；有电子化报送规定的，还应按规定电子化报送。

**实施方式。** 将字段清单与各类报告准备流程绑定，准备允许使用的渠道及故障替代路径。电话报送建议同步记录接报对象、时间和实际内容；邮件和传真后保留电话或即时通信确认。未知信息如实标识、持续补充，不得编造完整性，也不能以填满最终信息为前提拖延报告。

**完成标准。** 每次报送的内容、对象、时间和渠道可核验，适用的收悉、保密及盖章要求均完成。模板覆盖只能证明准备情况，还需验证真实报告。

**验证问题。** `IR-04-18`：四类报告准备是否逐字段覆盖要求，抽取的实际报告是否遗漏适用内容？`IR-04-16`：工作秘密报告是否使用合规渠道，备用路径能否验证？`IR-04-17`：邮件或传真报送后是否存在电话或即时通信确认，且能关联到该次报告？对指定系统单独核对规定和提交结果，不能默认系统回执可替代邮件、传真后的明确确认要求。

**证据。** 报告内容、字段核对、报送结果、接报对象、确认记录和盖章版本等。仅邮件“发送成功”不能证明完成收悉确认；合法电话、即时通信报送也不能仅因没有PDF被否定。只有内部群消息不等于向监管报告，通话记录本身也不一定能证明实际报告了哪些内容。

**依据。** [第18—21条](#law-18)。

#### 联动个人信息补救和通知义务 {#personal-information}

**法规要求。** 涉及个人信息泄露、篡改、丢失的，总结报告还应说明补救措施、依法通知个人的情况，以及告知个人可采取减轻危害措施的情况。重大以上事件应在进展报告中提前说明，不能一律等到事后总结。

并行适用个人信息保护法第57条时，发生或者可能发生个人信息泄露、篡改、丢失，应立即采取补救措施并通知履行个人信息保护职责的部门和个人。采取措施能够有效避免危害时，可以不通知个人，但主管部门认为可能造成危害的，有权要求通知。该例外不当然免除主管部门通知义务。

**实施方式。** 将安全调查、隐私影响评估、部门通知和个人通知分别建立任务。通知内容覆盖信息种类、原因和可能危害、补救及个人减损措施、处理者联系方式。不通知个人时，形成事实和适用依据，不能仅以影响较小或担忧舆情作为理由。

**完成标准。** 对每起相关事件可说明是否通知、向谁通知、何时通知及其依据；实际补救与报告描述一致。重大以上事件的进展报告已体现当时应说明的内容。

**验证问题。** `IR-04-19`：抽取通知和未通知个人的事件，分别检查补救、法律判断、实际通知、必要字段及报告呈现；不得把“已作判断”视为所有应执行动作均完成。

**证据。** 影响和补救验证、适用性判断、通知内容及执行记录、进展和总结报告。不适用某项通知义务须说明依据，模板本身不证明已通知。

**依据。** [第4条](#law-4)、[第20条](#law-20)；并行依据为[《个人信息保护法》第57条](https://www.cac.gov.cn/2021-08/20/c_1631050028355286.htm)，应与4号令要求分别登记。

### 调查与留存 {#investigation-and-records}

#### 完成调查总结、延期承诺和退回修订 {#post-incident}

**法规要求。** 事件处置结束后10个工作日内报送调查总结。无法按时完成时，先按时报送初步报告，说明最终报告承诺日期并按时履行；承诺日期原则上在处置结束之日起40个工作日内。收到正式退回修改意见后，应在收到反馈之日起10个工作日内完善并重新报送。

第17条未将事后调查总结限定为较大以上事件。一般事件也不能仅因不适用第15条第一款首报时限就跳过总结。报告内容和形式见[报告内容及渠道](#report-content-and-channels)。

**实施方式。** 分别记录业务恢复、事件处置结束、整改完成等状态，避免用任意关闭工单日期代替处置结束。建立工作日截止日期、初步报告、承诺及退回反馈台账；复杂事项的起止依据由责任人和法务合规核实。

**完成标准。** 已结束事件的报告按适用期限和形式提交；延期既有按时初报，也有履行承诺的终稿。延后提交不应仅用“原则上40个工作日”自行豁免，应有具体适用依据并核实监管要求。

**验证问题。** `IR-04-20`：从全部已处置结束的适用事件中核对总结，分别判断按期报送、内容、形式；延期事件继续检查承诺是否履行。`IR-04-22`：全部正式退回事项是否逐条回应并按期重报？不能只检查已完成终稿而漏掉仍挂起的事件。

**证据。** 处置结束事实、期限计算、初步和最终报告、提交结果、承诺日期、监管反馈及修订差异。内部复盘完成不等于总结已对外报送，终稿已写完不等于承诺已经履行。

**依据。** [第17—19条](#law-17)、[第23条](#law-23)。

#### 形成责任认定和差异化处理依据 {#accountability}

**法规要求。** 较大以上事件总结还应包括直接负责的主管人员和其他直接责任人员的责任认定及处理情况。制度应综合动机态度、客观条件、程序方法、后果影响和挽回损失等因素，明确差异化处理情形。适用第22条减轻或免除责任处理时，须能提供证明并在总结中说明。

**实施方式。** 预先建立责任处理规则，由调查事实支持责任结论。对主动报告并立即处置、符合条件的创新试错、已履行制度规程等情形分别核实，不预设“发生事件必定处罚某个人”。机构按第22条作出的责任处理减免，不等于行政法律责任自动免除。

**完成标准。** 责任结论、制度依据、事实证据、处理或减免理由能对应，适用内容进入对外总结。不能只有技术根因，也不能只有处分名单。

**验证问题。** `IR-04-21`：检查较大以上事件是否逐一形成规定人员的责任判断；实际处理是否符合制度，减轻或免除时是否有证据且在总结中说明？结论中的每项判断分别可复核。

**证据。** 职责、制度、调查事实、责任认定、处理或减免依据、总结中的相关内容。口头决定或无事实支持的免责说明不足。

**依据。** [第21—22条](#law-21)。

#### 核查监管风险提示并反馈 {#regulatory-notices}

**法规要求。** 收到人民银行通报的运行异常、疑似泄露、安全缺陷、漏洞等风险提示后，立即组织核查并采取必要补救。风险属实且构成事件的，依本办法报告；风险不属实或尚不构成事件的，仍按通报要求及时反馈核查处置情况。

**实施方式。** 对接收、分派、核查开始、结果、补救和反馈建立记录。将“开始核查”“完成处置”“到期反馈”分别管理，不能把立即核查误写成所有调查和整改都须瞬间完成。构成事件时关联分级与报告任务。

**完成标准。** 每条通报均有核查结论和适用的反馈；未构成事件也不丢失后续责任。风险尚未排除或整改未完成时，继续跟踪并按要求说明进展。

**验证问题。** `IR-04-23`：从接收端选取属实、不属实、尚未完成核查的通报，逐条核对启动时间、必要补救、事件判断、反馈期限和实际结果。

**证据。** 原始通报及期限、责任分派、核查和补救记录、判级或排除依据、反馈材料及提交结果。邮件转发或内部标为“已解决”不能替代对外反馈。

**依据。** [第24条](#law-24)。

#### 建立可追溯的事件台账和证据索引 {#records}

**法规要求。** 建立事件台账，完整准确记录事发时间、事发报告时间、人民银行接报联系人及对应报告内容；台账至少留存三年。

**实施方式。** 用事件编号或稳定关联关系串联原始线索、影响数据、判级、报告和事后处理。台账可以使用适当的系统或受控表格，重点是记录完整、访问受控、能够检索和迁移。建议保存可核验的报告内容及关联证据；其他原始日志的保存期限还须按其适用规定确定，不能把“台账三年”机械等同于所有日志三年。

**完成标准。** 应记录事件不遗漏；记录和附件可查、可关联、不因换人或迁移丢失。检查留存时区分本办法施行后的记录、施行前其他规则要求保留的记录和机构成立时间；没有自然积累满三年，不直接判定不合格。未触发某类报告或责任认定的事件，记录适用依据，不强行制造不存在的材料。

**验证问题。** `IR-04-24`：核查台账字段、保存策略及各适用期间现存记录，是否存在提前删除或不可恢复的缺失？`IR-04-25`：由检查方从独立来源选定一个事件，是否能从事实与判级追到各项适用动作和证据，未适用阶段是否说明理由？

**证据。** 台账、证据索引、报告内容、接报记录、保存和迁移验证。散落消息无法关联不够；单有统一平台，也不能证明内容完整。证据不足应明确标记，不能靠事后补造历史材料通过检查。

**依据。** [第25条](#law-25)；相关动作分别回到其适用条款。

## 检查与验收 {#assurance}

本节规定如何组织一次检查。每项要求的具体问题和证据已在前文列出，这里只统一检查范围、样本、场景和结论规则。

### 确定范围、材料和验收口径 {#test-rules}

检查前明确机构、业务、系统、期间、法规版本、内部标准和复核人。先建立每条适用义务到实施成果、测试项及证据的映射，再开展测试。第26条要求配合人民银行依法实施的检查；`IR-04-31`用于核验是否按实际检查要求提供真实、可追溯材料并跟踪答复，不能仅以“已建立材料目录”判定已配合。

建议从前述四个工作主题收集最小材料包：范围与职责、分级规则和指标来源、报告及监管反馈、事件总体和证据索引。检查人员不得只接收被检查方挑选的“最佳案例”，也不应收集超出必要范围的个人信息、秘密或敏感架构。

法定义务与内部能力基线分别登记、分别判定：

| 类别 | 如何使用 |
| --- | --- |
| 法定义务 | 使用本办法及其他适用规定的准确条件和时限。内部审批不能豁免；不能用建议指标替代法规原文 |
| 内部能力基线 | 例如15分钟取得适用判级数据、5分钟定位报告渠道、每6个月验证联系人；均为建议示例。机构在测试前明确目标、起止点、范围和批准版本，不在失败后临时降低标准 |
| 检查方法 | 抽样数量、现场用时、演练方式由检查计划确定，不冒称法定检查频次或样本量。只得到样本结论时，不写成全量合规结论 |

依法要求每年评估与内部“最近12个月评估”不是同一表述，应分别核对；未修改标准可有不变更的评估结论。演练验证属于本页的能力检查建议，4号令第13、15条未单独规定一套固定演练频次或“无事件必须用演练凑足三起”的要求。其他法规另有演练义务时另行登记。

### 先验证总体完整，再抽查执行结果 {#population-and-sampling}

先取得业务、系统、生产故障、告警、投诉、数据异常、舆情和监管通报等来源清单，与事件台账交叉核对。发现未登记线索时，查其排除或判级依据；先解决样本总体明显不完整的问题，再评价报送执行效果。

对报告时效，建议在检查期间内全量核对达到第15条条件的事件，包括舆情触发情形，并覆盖第16条适用的全部进展期间。内容和证据可按风险分层抽查，至少考虑不同等级、数据与非数据、攻击与非攻击、不同渠道、一般事件、延期、退回及未报告判断。样本数量取决于总体和风险，不固定为最近三起。

若只能抽样，底稿记录总体规模、来源、样本选择依据、覆盖边界和未查部分。发现偏差后扩大核查；三起通过只证明三起的结果，不能代替“全部事件均按时”的证据。无样本时先核实是真的没有事件，还是来源未覆盖、台账漏记或资料丢失。

### 用场景检验跨环节能力 {#scenario-tests}

`IR-04-10`用于全链路能力测试，与真实事件检查单独出结论。使用已授权的隔离环境、真实岗位分工和拟用模板，向模拟接报端提交；未经事先约定，不向监管发送虚构事故，也不为演练制造生产故障。

以下为建议的测试场景。所有预期均以给定事实及无其他更高等级条件为前提，实际事件还须综合适用条款。

| 场景 | 应验证的结果 |
| --- | --- |
| 纯发布故障，支付相关网络在高峰期单省整体中断35分钟 | 不因无攻击跳过判级；按适用中断条件至少较大，进入相应报送流程 |
| 正常业务量10000笔，成功2000笔、未处理8000笔、失败0笔 | 计算出80%的未处理和失败比例，继续核对整体中断的其他前提 |
| 单省高峰中断尚未达到30分钟，但主要功能异常已实际影响10万自然人正常开展业务 | 独立命中用户影响条件，不能因时长未达门槛而排除较大 |
| 已确认重要数据泄露，涉及规模很小 | 按重要数据条件至少重大，不能仅按普通个人信息数量降级 |
| 有效凭证暴露且可访问个人信息，下载情况待查 | 及时核查并进入适用分级；确有事件而对照标准无法准确判级时使用第12条兜底，不机械把所有凭证告警直接定为较大 |
| 不属于特定高峰中断表范围的金融服务网络，主要功能单省整体中断30分钟 | 检查第10条的一般条件及其他条件，不以“不适用高峰表”跳过处理、总结和台账 |
| 技术影响未达较大，但出现第15条第二款所述较大舆情 | 执行相应首报义务；不把报告触发与技术等级混为一谈 |
| 共同基础设施故障影响多个网络，后续其中一个升级为重大 | 分别判级、整体取最高、及时升级，进展报告与其他处置并行 |
| 主审批人不可达或主渠道故障 | 在合法授权内使用可用替代路径，验证时效、内容及适用收悉要求 |
| 无真实事件，或者存在未确认起算点的历史事件 | 前者分别记录无运行样本和演练结果；后者保留事实与争议，不能用新演练或自定起点覆盖历史问题 |

计时测试记录注入条件、操作、取数和报送结果；时间压缩的桌面推演应声明压缩方式，不能声称已经证明同等真实时长下的连续值守能力。选择已满足报告触发条件的注入场景时，可检验一小时窗口内完成模拟报送的能力，但该结果不替代真实事件的法定起算审查。

### 判断证据和替代实现 {#evidence-rules}

证据应说明来源、对象、发生时间、覆盖期间和关联关系，能够支持对应事实。可以采用依法留存的系统记录、往来消息、文件、人工操作和复核记录等组合；没有指定工具或文件名，不直接等于缺口。单张截图、模板、口头承诺和测试成功，分别不能单独证明长期覆盖、真实执行或历史报送合规。

替代实现先判断是否触犯法规明确限制，再核对结果、证据、稳定运行和可重复测试四方面。人工统计、不同平台关联、合法电话报送均可检验；法定时限、对象、禁止的渠道或明确的确认动作，不能仅靠内部“风险接受”替换。具体例外必须有适用依据。

### 分别形成结论并复测整改 {#results}

每个测试点记录范围、条款或内部基线、观察事实、证据引用和独立结论。复合问题拆分，例如报送时效、内容、渠道和收悉分别判断，避免“内容完整但迟报”被综合成基本通过。

| 结论维度 | 记录方式 |
| --- | --- |
| 适用性 | 适用、不适用或待核实，并记录依据；资料缺失不能填不适用 |
| 控制设计 | 按该项标准记录通过、未通过或未能验证 |
| 真实运行 | 按检查期间和样本记录通过、未通过、未能验证；经核实无相应事件时单独注明无样本 |
| 场景验证 | 单独记录通过、未通过或未测试，保留场景和测试限制 |
| 整改与复测 | 发现项、风险、责任人、期限、补救措施、复测证据和关闭结论 |

可复制的单项底稿字段：

```text
要求/测试编号：
检查对象与期间：
依据类型、条款/内部标准及版本：
适用性与理由：
总体来源、规模和样本选择：
应满足的条件：
观察事实、时间依据和证据位置：
设计结论 / 真实运行结论 / 场景验证结论：
未覆盖部分与待核实事项：
缺口、责任人、整改期限及复测结果：
检查人、复核人及日期：
```

历史漏报、迟报和证据缺失如实记录，整改后重新验证当前控制，不能把整改结果倒写成历史合规。证据不足意味着未能验证，不应无依据认定已经违法，也不能据此宣布通过。

机构可以标识内部关键控制决定整改优先级，但不能把其他法定义务视为可忽略事项，也不能用平均通过率抵消任何已发现的不符合。最终报告应说明适用范围、已检验事实、现存缺口和保证边界，不作“一定通过监管检查”的承诺。

### 第一章 总 则

- <span id="law-1"></span> **第一条** 为规范中国人民银行业务领域网络安全事件报告管理，根据[《中华人民共和国网络安全法》](./网络安全法.md)、[《中华人民共和国数据安全法》](./数据安全法.md)、[《中华人民共和国个人信息保护法》](./个人信息保护法.md)、《中华人民共和国中国人民银行法》等法律、行政法规，制定本办法。
- <span id="law-2"></span> **第二条** 金融从业机构在中华人民共和国境内发生中国人民银行业务领域网络安全事件时，应当按照本办法规定向中国人民银行或者住所地中国人民银行分支机构报告。非中国人民银行业务领域网络安全事件无须按照本办法规定报告。涉及国家秘密的，按照有关规定执行。
- <span id="law-3"></span> **第三条** 本办法所称中国人民银行业务领域，指依据法律、行政法规，党中央、国务院决定，由中国人民银行承担监督和管理职责的业务领域。
  - 本办法所称中国人民银行业务领域网络安全事件（以下简称网络安全事件），指由于人为原因、遭受网络攻击、存在漏洞隐患、软硬件缺陷或故障、不可抗力等因素，对本机构建设、运营、维护、管理的中国人民银行业务领域网络或者处理的中国人民银行业务领域数据造成危害的事件。
- <span id="law-4"></span> **第四条** 国家有关部门和其他金融管理部门等对网络安全事件报告有规定的，金融从业机构还应当从其规定报告。涉及危害计算机信息系统等违法犯罪的网络安全事件，金融从业机构还应当及时向公安机关报案。
  - 中国人民银行加强与国家有关部门和其他金融管理部门间的网络安全事件报告内容共享，按照国家有关部门规定向其通报网络安全事件，并根据其他金融管理部门需要向其通报网络安全事件。
- <span id="law-5"></span> **第五条** 任何个人和组织有权向中国人民银行或其分支机构举报金融从业机构未按照本办法规定报告网络安全事件的行为。中国人民银行或其分支机构对举报人的相关信息予以保密。

### 第二章 网络安全事件分级

- <span id="law-6"></span> **第六条** 金融从业机构应当在本机构网络安全管理制度或者操作规程中明确网络安全事件分级标准（以下简称分级标准），将网络安全事件分为特别重大、重大、较大和一般四个等级。金融从业机构应当每年组织评估并视情更新分级标准。分级标准如有更新，应当报本机构主管网络安全的领导班子成员批准。
  - 金融从业机构制定分级标准时，应当综合考虑网络安全事件对业务、用户等的影响程度。金融从业机构针对与货币存取款、支付交易、税款缴库、银行间市场交易密切相关的中国人民银行业务领域网络制定分级标准时，应当差异化考虑业务高峰时段和非业务高峰时段网络安全事件对业务处理的影响程度。
  - 金融从业机构还应当结合中国人民银行业务领域数据安全管理相关规定，制定与中国人民银行业务领域数据遭到篡改、破坏、泄露相关的分级标准。
  - 金融从业机构可以针对网络安全等级保护三级以上的中国人民银行业务领域网络，逐一细化制定专门适用的分级标准。
- <span id="law-7"></span> **第七条** 符合下列情形之一的，应当分级为特别重大网络安全事件：
  - （一）属于金融基础设施、直接服务5000万个以上自然人或者与货币存取款、支付交易、税款缴库、银行间市场交易密切相关的中国人民银行业务领域网络，主要功能在业务高峰时段出现两个以上省级行政区范围整体中断运行3小时以上或者单个省级行政区范围整体中断运行6小时以上的；
  - （二）提供金融服务的中国人民银行业务领域网络，主要功能出现中断、超时报错等情形，导致业务无法正常开展，经合理测算或者估算，已实际影响1000万个以上自然人或者100万个以上法人和其他组织的；
  - （三）中国人民银行业务领域核心数据遭到篡改、破坏、泄露的；
  - （四）致使泄露1000万条以上敏感个人信息或者1亿条以上个人信息的；
  - （五）网信部门、公安机关已明确应当分级为特别重大网络安全事件的；
  - （六）中国人民银行或其上海总部、省级分行、计划单列市分行研判并书面告知金融从业机构，应当分级为特别重大网络安全事件的。
- <span id="law-8"></span> **第八条** 符合下列情形之一的，应当至少分级为重大网络安全事件：
  - （一）属于金融基础设施、直接服务5000万个以上自然人或者与货币存取款、支付交易、税款缴库、银行间市场交易密切相关的中国人民银行业务领域网络，主要功能在业务高峰时段出现两个以上省级行政区范围整体中断运行1.5小时以上或者单个省级行政区范围整体中断运行3小时以上的；
  - （二）提供金融服务的中国人民银行业务领域网络，主要功能出现中断、超时报错等情形，导致业务无法正常开展，经合理测算或者估算，已实际影响100万个以上自然人或者10万个以上法人和其他组织的；
  - （三）中国人民银行业务领域重要数据遭到篡改、破坏、泄露的；
  - （四）致使泄露100万条以上敏感个人信息或者1000万条以上个人信息的；
  - （五）网信部门、公安机关已明确应当分级为重大网络安全事件的；
  - （六）中国人民银行或其上海总部、省级分行、计划单列市分行研判并书面告知金融从业机构，应当分级为重大网络安全事件的。
- <span id="law-9"></span> **第九条** 符合下列情形之一的，应当至少分级为较大网络安全事件：
  - （一）属于金融基础设施、直接服务5000万个以上自然人或者与货币存取款、支付交易、税款缴库、银行间市场交易密切相关的中国人民银行业务领域网络，主要功能在业务高峰时段出现两个以上省级行政区范围整体中断运行15分钟以上或者单个省级行政区范围整体中断运行30分钟以上的；
  - （二）提供金融服务的中国人民银行业务领域网络，主要功能出现中断、超时报错等情形，导致业务无法正常开展，经合理测算或者估算，已实际影响10万个以上自然人或者5000个以上法人和其他组织的；
  - （三）致使泄露500条以上征信信息、财产信息，或者致使泄露5万条以上个人信息的；
  - （四）遭受勒索恶意程序攻击，已对中国人民银行业务领域网络或者中国人民银行业务领域数据造成危害后果的；
  - （五）网信部门、公安机关已明确应当分级为较大网络安全事件的。
- <span id="law-10"></span> **第十条** 符合下列情形之一的，应当至少分级为一般网络安全事件：
  - （一）提供金融服务的中国人民银行业务领域网络，主要功能出现单个省级行政区范围整体中断运行30分钟以上的；
  - （二）提供金融服务的中国人民银行业务领域网络，主要功能出现中断、超时报错等情形，导致业务无法正常开展，经合理测算或者估算，已实际影响1万个以上自然人或者1000个以上法人和其他组织的；
  - （三）中国人民银行业务领域网络主要功能出现中断、超时报错等情形，导致业务无法正常开展，已持续1小时以上的；
  - （四）中国人民银行业务领域数据遭到篡改、破坏、泄露，导致社会危害的；
  - （五）发生或者可能发生个人信息泄露、篡改、丢失的；
  - （六）网信部门、公安机关已明确应当分级为一般网络安全事件的。
- <span id="law-11"></span> **第十一条** 金融从业机构制定与中国人民银行管理的金融基础设施业务交互功能异常相关的分级标准时，应当征求金融基础设施运营机构意见并协商一致。
- <span id="law-12"></span> **第十二条** 金融从业机构发生网络安全事件时，应当对照分级标准，综合确定网络安全事件等级。同时符合多个分级标准的，应当按照最高级别确定网络安全事件等级。对照分级标准无法准确确定网络安全事件等级的，应当至少分级为较大网络安全事件。
  - 因灾害或者信息基础设施故障，导致金融从业机构多个中国人民银行业务领域网络同时发生网络安全事件时，应当先分别确定网络安全事件等级，再按照各网络安全事件等级中的最高级别，确定整体的网络安全事件等级。
  - 网络安全事件事态发展情况已达到更高级别分级标准时，金融从业机构应当立即调整网络安全事件等级。

### 第三章 网络安全事件报告

- <span id="law-13"></span> **第十三条** 金融从业机构应当明确应急处置与报告的职责分工，确保网络安全事件报告及时、准确、完整，不得迟报、漏报或者瞒报。
  - 金融从业机构应当健全网络安全风险监测预警体系，提升第一时间发现和报告网络安全事件的技术能力。
  - 金融从业机构发生网络安全事件时，应当立即启动应急预案，采取相应的补救措施。按照本办法规定报告网络安全事件时，不应迟滞业务恢复、存证溯源、用户解释、舆情应对等处置工作。
- <span id="law-14"></span> **第十四条** 国家开发银行、政策性银行、国有商业银行、中国邮政储蓄银行、股份制商业银行、属于系统重要性金融机构的城市商业银行、系统重要性非银行支付机构、经营个人征信业务的征信机构发生网络安全事件时，应当向中国人民银行报告；其分支机构发生网络安全事件时，应当向住所地中国人民银行分支机构报告。中国人民银行所属单位及其管理的金融基础设施运营机构发生网络安全事件时，应当向中国人民银行报告。其他金融从业机构或其分支机构发生网络安全事件时，应当向住所地中国人民银行分支机构报告；在保障报告时效性前提下，证券、期货、基金机构发生网络安全事件时，经中国证监会派出机构转通报同级中国人民银行分支机构。
  - 中国人民银行计划单列市分行（不含深圳市分行）、地市分行接报辖区发生较大等级以上网络安全事件时，应当及时上报至中国人民银行省级分行。中国人民银行省级分行、深圳市分行接报辖区发生重大等级以上网络安全事件时，应当及时上报至中国人民银行。
- <span id="law-15"></span> **第十五条** 金融从业机构发生较大等级以上网络安全事件后，应当于1小时内报送网络安全事件事发简要报告，并在24小时内报送网络安全事件事发报告。
  - 金融从业机构发生网络安全事件，尚未达到较大等级，但出现相关舆情信息进入社交媒体、搜索引擎或者新闻网站热点榜等情形，引发较大舆情的，应当按照前款规定报告。
- <span id="law-16"></span> **第十六条** 对于重大等级以上网络安全事件，金融从业机构应当至少每隔2小时进行事中进展报告，直至处置结束。处置过程中如出现调高网络安全事件等级、处置取得阶段性进展、发现新的问题等重要情况时，应当立即报告。
- <span id="law-17"></span> **第十七条** 网络安全事件处置结束后，金融从业机构应当于10个工作日内报送事后调查总结报告。无法按时报送事后调查总结报告的，金融从业机构应当先按时报送初步报告，说明承诺报送事后调查总结报告的日期并按时报送。承诺日期原则上应当在处置结束之日起40个工作日内。
- <span id="law-18"></span> **第十八条** 金融从业机构可以通过电话、即时通信工具、电子邮件、传真或者中国人民银行指定的信息系统报送网络安全事件事发简要报告、事发报告和事中进展报告；采用电子邮件、传真方式报告的，应当通过电话或者即时通信工具确认中国人民银行或其分支机构已收悉。涉及工作秘密的，不得通过互联网渠道报告。
  - 金融从业机构应当书面报送网络安全事件事后调查总结报告，并加盖本机构或者承担报告职责内设部门公章。中国人民银行对网络安全事件事后调查总结报告另有电子化报送规定的，金融从业机构还应当按照规定电子化报送。
- <span id="law-19"></span> **第十九条** 网络安全事件事发简要报告内容包括初次确定的网络安全事件等级、事发时间、依据网络安全事件分类分级相关国家标准确定的网络安全事件分类、影响的中国人民银行业务领域网络及其对应的网络安全保护等级、涉及的数据中心、报告机构和报告时间、报告人和联系方式。网络安全事件事发报告应当在事发简要报告内容基础上，增补影响范围和程度、已采取的措施和效果，网络攻击事件还应当增补分析研判情况。
  - 网络安全事件事中进展报告应当在事发简要报告基础上，增补说明最新确定的网络安全事件等级、影响的变化、处置进展和下一步拟采取的措施。如存在需中国人民银行或其分支机构协调支持处置的事项，应当一并说明。
  - 网络安全事件事后调查总结报告内容应当包括最终确定的网络安全事件等级、处置历程回顾、影响损失评估、技术或者管理问题根源分析、处置经验教训、后续改进措施、报告机构和报告时间、报告人和联系方式、签发人。
- <span id="law-20"></span> **第二十条** 金融从业机构发生网络安全事件涉及个人信息泄露、篡改、丢失的，事后调查总结报告还应当说明本机构为有效避免网络安全事件危害所采取的补救措施、依法通知个人的情况和告知个人可以采取减轻危害措施的情况。
  - 对于重大等级以上网络安全事件，前款所列内容应当在事中进展报告中提前予以说明。
- <span id="law-21"></span> **第二十一条** 较大等级以上网络安全事件事后调查总结报告内容，还应当包括直接负责的主管人员和其他直接责任人员的责任认定和对应责任处理情况。
  - 金融从业机构应当综合考虑动机态度、客观条件、程序方法、后果影响、挽回损失等因素，在本机构网络安全管理制度中明确责任处理的差异化适用情形。事后调查总结报告中对直接负责的主管人员和其他直接责任人员的处理措施，应当符合本机构网络安全管理制度规定。
- <span id="law-22"></span> **第二十二条** 满足下列条件之一并且能提供相关证明材料的，金融从业机构可以根据直接负责的主管人员和其他直接责任人员具体承担职责，视情针对性减轻或者免除责任处理，但应当在网络安全事件事后调查总结报告中予以说明：
  - （一）已按本办法规定主动报告，同时按照本机构网络安全事件应急预案有关程序立即进行处置，尽最大努力降低影响的；
  - （二）网络技术创新和应用过程中因缺乏经验、先行先试造成网络安全事件，且没有主观过错的；
  - （三）已切实落实中国人民银行和本机构网络安全、数据安全相关管理制度要求，并严格执行本机构相关操作规程的。
- <span id="law-23"></span> **第二十三条** 中国人民银行或其分支机构认为金融从业机构网络安全事件事后调查总结报告存在内容缺失、原因分析不清、影响损失评估失实、责任认定或者处理不当等情形，退回事后调查总结报告并正式反馈修改意见的，金融从业机构应当在收到反馈之日起10个工作日内完善事后调查总结报告并重新报送。
- <span id="law-24"></span> **第二十四条** 金融从业机构收到中国人民银行或其分支机构通报的其网络产品、服务存在运行异常、疑似数据泄露、安全缺陷、漏洞等风险提示时，应当立即组织核查，采取必要补救措施。经核查风险属实并构成网络安全事件的，金融从业机构应当按照本办法规定进行报告；风险不属实或者尚不构成网络安全事件的，应当根据通报要求按时反馈风险核查处置情况。
- <span id="law-25"></span> **第二十五条** 金融从业机构应当建立网络安全事件台账，完整准确记录网络安全事件事发时间、事发报告时间、中国人民银行或其分支机构接报联系人和对应的网络安全事件报告内容。中国人民银行分支机构应当相应建立辖区网络安全事件台账。台账应当至少留存三年。

### 第四章 法律责任

- <span id="law-26"></span> **第二十六条** 中国人民银行或其分支机构根据金融从业机构报告处置网络安全事件的情况，可以按照中国人民银行执法检查有关规定明确的程序，对金融从业机构依法实施检查，金融从业机构应当予以配合。
  - 金融从业机构拒绝、阻碍中国人民银行或其分支机构实施检查的，中国人民银行或其分支机构依照[《中华人民共和国网络安全法》](./网络安全法.md)第六十九条予以处罚。
- <span id="law-27"></span> **第二十七条** 金融从业机构未按照本办法规定报告网络安全事件的，中国人民银行或其分支机构依照[《中华人民共和国网络安全法》](./网络安全法.md)第五十九条予以处罚。
  - 前款行为涉及中国人民银行业务领域数据遭到篡改、破坏、泄露或者非法获取、非法利用的，中国人民银行或其分支机构依照[《中华人民共和国数据安全法》](./数据安全法.md)第四十五条予以处罚；前款行为涉及个人信息泄露、篡改、丢失的，中国人民银行或其分支机构可以依照[《中华人民共和国个人信息保护法》](./个人信息保护法.md)第六十六条予以处罚。
- <span id="law-28"></span> **第二十八条** 金融从业机构收到中国人民银行或其分支机构通报的风险，如果风险属实，但未立即采取补救措施或者未按照本办法规定按时反馈核查处置情况的，中国人民银行或其分支机构依照[《中华人民共和国网络安全法》](./网络安全法.md)第六十条予以处罚。
  - 有前款行为并且通报的风险为数据安全缺陷、漏洞的，中国人民银行或其分支机构依照[《中华人民共和国数据安全法》](./数据安全法.md)第四十五条予以处罚。
- <span id="law-29"></span> **第二十九条** 金融从业机构在接受中国人民银行或其分支机构检查时，主动供述检查人员尚未掌握的未按照本办法规定报告网络安全事件行为的，应当从轻或者减轻处罚。
- <span id="law-30"></span> **第三十条** 中国人民银行分支机构未按照本办法规定报告网络安全事件，存在失职失责行为，造成重大损失、严重后果或者恶劣影响的，对直接负责的主管人员和其他直接责任人员依规依纪依法予以严肃追责问责。

### 第五章 附 则

- <span id="law-31"></span> **第三十一条** 本办法下列用语的含义：
  - （一）金融从业机构，是指金融机构以及经中国人民银行批准设立或者认定的其他机构。
  - （二）网络，是指由计算机或者其他信息终端及相关设备组成的按照一定的规则和程序对信息进行收集、存储、传输、交换、处理的系统。
  - （三）业务高峰时段，是指按年度统计的分时平均业务量超过日平均业务量百分之三的时段，或者依据本机构制度列明的其他合理计算方式确定的时段。
  - （四）整体中断运行，是指因网络安全事件，某一时段内未处理和处理失败业务量与正常情况全部业务量的比例，经合理测算或者估算，已经超过百分之七十。
  - （五）主要功能，是指与用户身份认证或者业务交互相关的功能。
  - （六）本办法所称“以上”均含本数。
- <span id="law-32"></span> **第三十二条** 本办法由中国人民银行负责解释。
  - 中国人民银行分支机构自身发生的网络安全事件应当向其上级行报告，报告时效、途径和内容等要求按照本办法对金融从业机构的规定执行。
- <span id="law-33"></span> **第三十三条** 本办法自2025年8月1日起施行。《银行计算机安全事件报告管理制度》（银发〔2002〕280号文印发）、《中国人民银行计算机系统信息安全报告制度》（银发〔2010〕366号文印发）同时废止。
