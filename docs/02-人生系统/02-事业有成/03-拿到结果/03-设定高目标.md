# 设定高目标

指标齐全，不代表目标正确。安全团队可以修复很多漏洞、提高自动化比例，却仍然遗漏最重要的风险。目标设定首先要判断值得改变什么，再决定用哪些证据检查改变。

我在安全建设中的体会是：工作量指标容易收集，风险改善却更难证明。仅用易统计的数字评价工作，会让团队优先完成可计数任务，忽略复杂但重要的问题。

如果需求仍停留在“建设平台”“提高效率”，先读[识别真正值得解决的问题](/problem-selection)确认问题与原因，再把有效方向转换成目标。目标设定不应替尚未验证的方案提前建立承诺。

## 从服务对象和瓶颈确定方向

理解上级目标背后的意图，同时核对客户、上下游与实际风险。问清谁受影响、损失在哪里、当前瓶颈是什么、团队能控制哪一部分。

例如应用安全的目标，可以是减少高影响风险进入生产环境，并降低遗漏风险造成损失的可能。它需要上线前治理，也需要运行期隔离、检测和响应，不能靠单一控制保证所有漏洞都无法利用。

## 分开愿景、阶段目标与护栏

长期愿景可以指向很高的标准，但阶段承诺必须匹配资源与证据。“零风险”只能作为理想方向，不能作为已经实现或可证明的状态。

设定目标时分别写出：期望变化、阶段范围、可用资源、完成期限及不能牺牲的条件。持续交付、服务可用性、隐私、工作负荷等可以成为护栏，防止团队为了一个指标把成本转移到别处。

挑战性目标适合探索和能力突破；合规、稳定性和明确交付义务往往需要可靠承诺。不能统一要求所有任务都“看起来不可能完成”。

## 指标同时覆盖结果与行动

结果指标检查价值是否实现，行动与覆盖指标检查是否按策略推进，两类应互相约束。例如评估上线前风险治理：

- **结果证据**：约定观察周期内，生产环境新发现的高影响软件风险数量与类型。需说明严重性判定、资产范围及发现渠道。
- **覆盖证据**：完成上线前风险评估的应评估接口数 / 本周期全部应评估接口数。范围清单与抽样质量需要核对。
- **修复证据**：在约定期限内修复并验证的风险数 / 本周期到期应处理风险数。延期与接受风险单独记录。
- **质量护栏**：评估带来的发布等待、误报和业务返工，防止把覆盖率建立在低质量检查上。

这些是指标设计示例，不是统一门槛。目标值应根据基线、风险容忍度和资源确定；没有外部发现的风险，不等于没有风险，需要授权测试与持续评估补充证据。

## OKR 与 KPI 都不能替代判断

OKR 用目标和关键结果表达期望变化，KPI 用指标观察运行或考核表现。两者都可能设计得合理，也都可能造成数字游戏。名称不能保证目标导向、参与度或客户价值。

参考[Google re:Work 的 OKR 实践说明](https://rework.withgoogle.com/intl/en/guides/set-goals-with-okrs)，使用时仍要明确本组织的评分和承诺规则。少量能支撑目标的关键结果，比穷尽所有工作清单更容易对齐。

## 让依赖方共同确认承诺

目标确定后，确认相关方提供什么、什么时候提供、由谁决策。不能把对方尚未同意的工作写成自己的确定计划。冲突需要协商优先级，或升级给有权配置资源的人。

用[持续拿到结果](/sustained-results)中的节奏检查策略与目标：指标达成却价值未变时，重查指标；目标仍重要但执行落后时，重查资源与方法。两种问题需要不同处理。
