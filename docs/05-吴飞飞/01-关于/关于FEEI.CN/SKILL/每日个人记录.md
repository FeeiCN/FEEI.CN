整理每日个人记录线索时使用，核对当天真实数据与活动，承接本人补充，并调用日记写作完成待审稿。交互任务按本次请求确定输入和交付；GitHub Actions 调用使用 workflow 提供的上下文，并遵循[自动化执行约定](/automation-execution-contract)。

流程分为自动采集线索、本人补充事实、整理成稿、PR 审阅四阶段；当前无人值守运行只完成自动采集，不虚构本人回答或直接拼成散文。

## 相关规则分工

| 规则 | 负责什么 | 何时读取 |
| --- | --- | --- |
| 每日个人记录（本文） | 采集线索、核对数据、维护当天 Issue、承接本人补充 | 每日自动采集和刷新，以及从记录进入成稿时 |
| 日记写作 | 选材、标题、组织正文、保留本人表达和成稿自审 | 已有本人补充，需要整理或修改日记时 |
| 每日三省吾身 | 综合客观数据与已记录事实，形成独立分析及行动建议 | 明确要求数据复盘时，日记成稿不强制调用 |
| 健康数据存储规范 | 来源路径、日期、分片及数据口径 | 读取健康、睡眠评分等数据时 |
| 通用写作、去AI味 | 事实与表达检查 | 成稿交付前 |
| 自动化执行约定 | 程序交付、版本校验、PR 与合并边界 | Actions 执行及 Issue 文件交付时 |

日记记录本人经历，三省报告提供分析；分析建议未经本人确认，不当作日记事实或行动承诺。github-issue-skill 用于一般 Issue 的知识沉淀，不作为每日记录的写作或发布入口。调度时刻、执行环境与恢复入口只在 workflow 和自动化运行维护。

## 自动采集

以 output/context.md 中固定的 target_date 为准，不因运行跨午夜而切换日期；先读已确认的当天记录和实际可访问的历史，避免重问。客观数据优先读取 output/personal-data-index.json 中已取回的文件，并依健康数据存储规范和 src/components/DailyRecordMeta.tsx 核对实际口径：睡眠评分为 /data/sleep-score/YYYY/MM/DD.json；健康为 /data/health/YYYY/MM/DD.json 日索引及其声明分片；阅读为 /data/reading/YYYY.json、/data/reading/weeks/YYYY.json。只有实际响应证明仍为旧版完整原始数据时，才使用旧月文件，不把月趋势缓存当事实源。

默认查看当日与必要的近 7 天趋势，确有意义才扩大至 30 天。按真实日期、单位、导出时间和覆盖情况核对睡眠、运动、步数、体重、阅读及目标相关的心情或用药记录。零与缺失、没有记录与没有发生必须区分；多来源不重复相加，状态冲突、跳变与同步滞后明确说明，不从缺失推断没服药、没睡觉或心情不好。采集不要求本人截图，读取失败说明实际失败层级和影响。

睡眠评分日期取来源 Issue 创建时间的北京时间日期，和健康日索引按日期关联，读取 provenance、observations 和 quality.warnings。手表关机可能影响评分时保留这一实际限制；“6小时”等 durationPrecision=display_hours 的摘要不能当作精确分钟数，不从关机时间推断醒来时间。不把评分与 Health Auto Export 分期时长混成同一项原始测量。

只读核对 FeeiCN 当天 00:00 至当前实际可访问的 GitHub 活动，优先本仓库，按目的合并真正进展，区分计划、提交、合并、构建与部署，过滤自动同步、重复构建及无关活动，不猜投入时长、情绪或意义。权限受限不以“未查到”推断“没做事”。

筛选与本人当天工作、投资、生活或出行直接相关的重要新闻、特殊日期、历史节点、异常事件和昨日未完事项。优先官方来源核对时间和证据；宁缺毋滥，不为覆盖 AI、安全、金融、杭州、天气等领域逐项凑新闻。普通发布、融资、论文或涨跌不自动进入日记。

## 本轮交付

每日 Issue 正文提供“今日主要做了什么”及本人回顾入口：是不是照顾好了自己、是不是照顾好了家人、是否推进了真正重要的事情、今天的选择是否让自己离四个目标更近一步，以及有哪些开心和不愉快的、明天可以提升什么。这些问题供本人填写，不由自动数据代答。将核实后的信息合并为最多三条有用线索，由固定程序更新 target_date 原 Issue 正文中的自动线索区块，自动数据快照折叠保留；不再另发线索、数据、进度或“已更新”等评论，旧评论保留。首次遇到旧版自动评论时，只将对应日期的最新机器人线索与数据复制到缺失的正文区块；同轮更新合为一次正文写入，不改本人内容或旧评论。正文已有区块优先，不用历史评论覆盖。不逐指标报表、不生成工作汇报，不默认所有客观数据都值得写入。已知事实供本人补充或纠正，不在自动线索中重复回顾问题或追加问卷。数据不完整但已有可靠线索时交付这些线索并说明缺口；关键数据完全未读到时返回 blocked，不能把空泛问题当作采集完成。来源与核验限制放在线索之后。交付必须绑定固定日期和原 Issue，缺少绑定就停止，不回退到通用新建 Issue 或评论；相同内容不写入，无变化保持静默。

## 数据刷新与延迟

晚间固定脚本刷新当天 Git 提交、Issue 创建/关闭和新增评论、健康日索引中的运动/步数/体重/睡眠、睡眠评分、阅读与各平台 Token 日期数据。自动线索和数据各自使用固定正文区块，刷新只替换对应区块，保留区块之外的本人填写与其他内容，不覆盖本人评论、已确认稿或网站文章；区块缺损、重复、正文并发变化或篇幅超限时停止更新，不截断或整篇重写。来源失败时保留上次成功快照并标明旧数据，缺失不记作零。各来源保留时间和口径；Token 平台账单日期不擅自换算成北京时间，不把自动提交或机器人评论当作本人工作成果。已发布日记的动态数据随原来源更新，正文内写死数字需提出修订，不能自动重写。GitHub cron 不保证准点，运行摘要记录计划时刻、运行创建、运行开始与实际采集时刻，不把所有时间差都称为排队。

## 本人补充后的成稿

本人编辑每日 Issue 正文或在评论中补充事实后，按日记写作完成选材、组织、标题和成稿自审；自动区块仅作核对线索，不当作本人叙述，机器人刷新不触发成稿。事实与表达遵循通用写作；日记修订在原 Issue 说明本轮改动，固定程序保存并展示完整稿件。本人可以连续补充或修改，定稿前不创建 PR。先完成内部成稿与自审，不分多条发送提纲、初稿和自评。本人主动追问或补充后可正常回复一次，自动刷新不触发回复或改稿。日记格式与合并继续遵循对应 SKILL 和本人对具体版本的确认。

## 确认写入

本人明确要求提交当前版本的 PR 后，固定程序先核验封存稿件和最新 main，再创建待审 PR。同一版本重试时复用符合核验条件的开放 PR。Issue 回复提供 PR 链接，合并由本人在 PR 中确认。日记文件、日期 slug、published_at、自然标题、location、day_status、icon 和 description 均遵循 SKILL 中既有规则，不另写一套格式。写入流程按共用约定核对最新 main 与当月目录，保留其他日期和已确认正文。
