FEEI.CN 是吴飞飞的个人知识与生活记录站，围绕健康、事业、财务、人生体验四个方向持续积累。这里同时保存按时间留下的生活记录，以及随认识更新的专题内容。新的想法优先融入已有专题，让零散的经历和思考逐步形成可以反复使用的认识。

## 为什么建立这个系统

我希望这个系统能帮我做好三件事：记住生活、改善选择、积累认识。

**记住生活。** 留下发生的事情、遇到的人，以及当时的感受与判断。几年后重新读到，仍能想起那段日子是怎么过的。这是日记的价值，不要求每一天都有进步，也不要求每一件事都总结出道理。

**改善选择。** 把日常经历与一段时间的数据放在一起，发现反复出现的问题，判断哪些做法有效，决定下一步调整什么。这是复盘的价值。记录不只是为了回头看，也为了让下一次选择多一些依据。

**积累认识。** 将已经想清楚、值得反复使用的方法，融入健康、事业、财务和人生体验的专题中。新的经历带来新的认识，旧的判断也可以被修正。这是知识积累的价值：经历没有停留在过去，而是成为以后遇到问题时可以调用的经验。

**日记保留“当时的我怎么想”，专题维护“现在的我怎么看”，复盘连接两者。** 客观数据为它们提供事实依据，但不替代感受，也不负责给生活打分。

## 我如何记录生活

我以日记为生活记录的基本单位，文字和照片为主，数据为辅。先把当天值得留下的事情记下来，再考虑以后怎样找到它们。这套方式在[日记和照片，不必一起完成](/2026-09-27)中记录了最初的取舍；这里维护现在采用的方式，不回头改写当时的认识。

### 一份经历，不重复写几遍

旅行中的事情已经写进每天的日记，回来后就不必再单独写一遍游记。同一次旅行的几篇日记连起来，就是完整的旅行记录。需要补充某件事，只改那一天，不必同步维护另一篇相似的文章。

“探索世界”也沿着这个方向组织：日记按时间读，足迹按地点看，让不同入口回到同一份记录。它不必以离开杭州为界，像[南湖露营](/2026-09-26)这样的本地经历也值得留下；但不是每次出门、每次通勤都要变成一条探索记录。

### 文字、照片和回顾，不必同时完成

我在手机相册里用收藏标记可以公开的照片，再通过手机工具上传到服务器。程序读取拍摄时间，转换、压缩照片，去除 EXIF 等元数据，生成按日期分组的索引。日记页面根据自己的日期读取对应照片，有图就展示，无图就保留文字。

文字写好了就先发，照片可以过几天再挑；照片先上传，日记也可以以后补。文章留在 Git 里，照片单独存放，日期负责关联。补照片不用逐篇粘贴链接，也不需要为了这件事再维护一套相册后台。公开范围由我选择，原片与备份另行保留；去除元数据不等于照片内容本身没有隐私。

月度和年度回顾可以晚些再做。它们从已经留下的日记、照片和必要数据中挑材料，写后来才看清的变化，而不是重抄一遍每天的事情。

### 记录不该变成维护负担

日記可以短，可以没有照片，也可以只有几件并列的小事。不要求每天写满，不为了健康、工作、财务等栏目凑内容，更不要求每次经历都得到一个道理。数据先少而有用，能自动获得的再自动获得，不把日记做成另一份报表。

AI 帮我核对公开信息与 GitHub 活动、整理已有叙述、安排轻重、删去重复。当天怎么过、哪些细节真实、哪些内容适合公开，仍然由我确认。补充细节后重新融合进完整草稿，明确确认后才写入，不用漂亮的句子替我补出没有发生过的事。

判断新功能是否值得做，就看它能否减少维护、帮助找回经历，或让下一次选择多一点依据。仅仅多一个数量、一张图表、一种打卡，不足以成为增加它的理由。

### 让旧记录更容易找回来

接下来可以先尝试让有照片、没写日记的日子也有入口，以及从一个地点回到相关日记。再往后，同一人物或宠物、反复思考的问题，也可以按时间串起来：回看几次到访的不同，找出什么时候开始注意到团子的变化，或追溯一个设计从困扰到取舍的过程。这些是后续设想，不代表已有完整功能。

先从检索做起，反复有用的查询再固定成入口，不急着增加必填字段。关联必须保留事实边界：日记提到旧事，不算当天到访；提到一个人，不等于当天见过他；未知日期、照片人物和地点不靠 AI 补全。

## 内容标准

**专题内容宁愿一篇写透，也不要十篇蜻蜓点水。** 覆盖面广不代表有洞见，浅入深出比面面俱到更有价值。

专题内容的六个标准：让人愿意读、读得懂、能相信、记得住、自带传播力、可触发行动。前三条是底线，后三条是追求。日记不承担传播或促进行动的任务，真实、清楚、值得自己重读就足够。

写作的基本要求对应信达雅：信（忠实内容）、达（表达通畅）、雅（符合阅读习惯）。前两条是底线，第三条是追求。

专题文章可以先给核心结论，再展开依据；日常记录顺着真实场景和事情发展来写，不必结论先行。用具体对象、动作和有依据的数字说明问题，不以空泛判断代替细节；表格以比较和查询为目的，兼顾手机竖屏阅读。

## 内容如何生产

专题想法的捕获与知识沉淀是两件独立的事，把它们混在一起成本太高——要想清楚放哪里、怎么表达、和现有内容的关系，这些判断成本会让大量想法在"该写但还没写"的状态里消失。本站把两件事分开处理：

**捕获极低摩擦。** GitHub Issue 是随时可以扔东西进去的收件箱——标题、几行文字、一张截图、一个链接，都行。不需要想结构，不需要想措辞，不需要想放哪里。

**整合由 LLM 完成。** 判断归属、提炼观点、找到现有文档的接入点、写成连贯的表达——这些认知成本交给 LLM。LLM 同时能看到全部待处理 issue 和全部现有内容，做的是真正的融合，不是简单追加。每一条想法都有最终去处（关闭），不会积压。

输入源分两类：

**思维与认知**——书摘划线、浏览器稍后阅读、视频文稿、突然的灵感、洗澡时的想法、对话中触发的认知……来源不固定，共同点是捕获窗口极短。比如微信读书 skill 可以直接把划线抓出来，创建成 GitHub Issue，先进入收件箱，再交给 LLM 处理。记下来是第一优先级，结构和措辞之后由 LLM 处理。LLM 的工作是逐条判断增量价值（重复或已覆盖则跳过），找到现有文档的接入点，融入而不追加——划线不是为了存档，而是为了让认知真正进入可被调用的结构中。

**客观数据**——投资持仓、iOS 健康数据、运动记录、睡眠数据……这类输入有明确的数据源和固定结构，用脚本自动同步比手动 Issue 更合适。以投资数据为例：脚本每天自动拉取证券账号持仓与历史资产，写入 `static/data/account-assets/` 下的 JSON 文件，MDX 页面通过 ECharts 渲染资产走势、持仓分布、盈亏明细。健康数据也是同一类流程：`sync-health` 先同步仓库，再调用 `export-health-year` 通过 health-auto-export MCP 读取 Apple Health 年度数据，写入 `static/data/health/<year>/<month>.json`，随后更新 FEEI.CN 运行状态页，提交健康数据和状态页并推送。页面本身只负责读取结构化 JSON 并渲染图表，数据全程不需要手动维护，变动会在下一次脚本运行后自动反映在站点中。

这套模式和"用 LLM 写 Wiki"的本质区别在于：LLM-Wiki 是让 LLM 生成内容，每次独立工作，不知道已有什么、该放哪里，久了知识库发散成积压库。这里的 LLM 是**编辑**——每次介入都读全量现有内容，判断新想法归属哪个文档的哪个位置，融入而不产生新页面。知识库的密度在增长，页面数几乎不变。结构由人定，内容由 LLM 填充，主权在人。

## 技术架构

**本站基于 Docusaurus，页面以静态文件对外提供，不依赖内容管理后台或数据库。** 文章以 Markdown 形式保存在 Git 中，照片等媒体独立存放，页面通过静态索引读取。服务器脚本负责媒体预处理，不需要为每次页面访问动态生成内容。

**选择这套架构的核心原因是 AI 友好。** 内容是纯文本 Markdown，AI 可以直接读取、撰写和重构，无需穿过编辑器、数据库或后台接口；各类信息都能以统一的 Markdown 沉淀下来，让 AI 参与整理与持续完善的成本极低。Git 与 Pull Request 的流程又让每次由 AI 产生的改动都可审阅、可回滚。

- 内容流程：编辑 Markdown / 源码 → 提交或合并 Pull Request → GitHub Actions 检查并构建 → 产出静态文件
- 照片流程：人工选择公开照片 → 上传 → 转换与建立索引 → 日记按日期读取
- 访问链路：用户 → HTTPS → Nginx → 静态文件
- 源码仓库：https://github.com/FeeiCN/FEEI.CN

公开新闻候选 0—3 条、特殊日期 0—2 条、历史节点通常 0—1 条、异常日 0—1 条、昨日连续性 0—2 条，全部宁缺毋滥。先问：“今天发生了哪些真正值得记住的事？”随后很短地给这些线索。没有关联的外部信息不写入日记，不要求逐条评论，不根据职业或投资关注推定态度。

按实际目的把多次提交、PR、关联 Issue 和修复归并为 0—3 件主要进展，回答“今天主要推进了什么，新增或完善了什么内容，解决了什么问题，还有什么未完成”，不用提交次数、文件数或代码行数替代总结，不逐条抄提交日志。准确区分内容新增、内容改写、目录搬迁、命名或展示调整；区分提出计划、已提交、已合并、构建成功和部署成功，未核实不称已完成。过滤无关他人活动、纯自动依赖更新、机械同步和重复构建；由 AI/机器人代为执行且与我的请求有明确关联的工作可计入，但不要写成我逐行手写，也不把仓库全部变化算成我的个人贡献。

将 GitHub 小结与当天已有对话交叉核对、去重，放在首次询问后的个人经历线索中，供我补充或纠正；不需要让我重新讲述已经核实的事实。用少量具体文章名、问题或改动结果帮助回忆，关键结论附可核对的提交或 PR 链接。GitHub 活动属于个人经历素材，不适用公开新闻的“大事记”门槛，但只选择对当天记录有价值的内容，不强行写入正文，不设置固定 GitHub 栏目，不据此推测投入时长、情绪或感悟。发现与昨天未完事项有关的变化，可并入既有“昨日连续性”线索，不额外扩张提问。无有价值活动可省略；权限、接口或检索失败，以及只覆盖部分仓库或时间范围时，明确说明限制，不能将“未查到”说成“今天没做事”，也不能用聊天记忆冒充已核实的 GitHub 活动。这一步只读，不自动修改代码、合并 PR、重跑 Actions 或写入日记。

【采集与补细节】结合当天已有对话与已核实的 GitHub 活动，先整理已经说过或查到的内容，再让我补充或纠正。区分本人明确叙述、可核实的客观记录和仍未知的细节；助手前文的推测不自动成为事实。重点采集事件、人物、对话、动作、数字、场景和当时真实念头，不做健康、工作、财务、感恩、反思等固定问卷。

材料足够就直接写，不为追求文采拖长采集。只有在现有叙述已给出明确线索、补充会显著改善文章时，才额外追问至多一个具体问题：例如某个关键动作或对话、最清楚的一处感官记忆，或同一地点让人想起的往事。不要同时列一串问题，不重问已知事实，不诱导情绪、意义或预设答案；没有补充也可以成稿。允许我看过草稿后再自然想起细节。

【选材定重心】先判断当天最值得留下的一至三件事，而不是按我讲述的长度平均分配篇幅。有一个鲜明场景时，让它成为主体，其他事情作为短段或背景；没有自然主线，允许几件事并列，也允许只有很短的一段。素材采集可以完整，正文不必面面俱到，但不能为突出主线删掉我明确要求保留的重要内容。

工作、GitHub 和数据记录写成当天具体做了什么、作了什么取舍，避免插入技术更新清单、会议纪要或绩效汇报。确有真实联系时与生活叙述衔接，没有联系就短写或另段，不制造因果或感悟。保留有辨识度的普通细节、轻微狼狈与反复，不只挑显得积极或正确的部分。

【写作】先写发生了什么，再让感受和判断自然出现。优先使用本人已提供的动作、声音、气味、触感、人物差异和原话，让场景成立，不用“很美、很幸福、很有意义”等概括替代细节。保留口语、轻微幽默、自嘲、犹豫和不确定，不把作者改写成过分文雅、通透或始终情绪正确的人。自然的反差和笑意由事实产生，不另添包袱或解释笑点。
