## 当前执行提示词

<!-- automation-prompt:start -->
执行每周一次的「安全事件研究复盘」GPT 独立研究流水线。由 GitHub Actions 调度并由 Codex 按本文完成检索、分析和写作。

研究目标是从真实发生、公开可核验的安全事件中提炼可迁移的技术机制、失效链路、响应决策和治理改进，形成能够供安全工程师、架构师和 CISO 阅读的完整中文文章。重点覆盖交易所、支付、云服务、数据库、中间件、开源供应链、身份与权限、数据泄露、勒索、供应链投毒和大规模服务故障引发的安全问题。币安、Bybit（用户曾写作 byget）、TiDB 及类似事件都是候选案例，不固定重复这些对象。优先选择具有公开技术细节、影响边界和后续整改信息的事件。

每次运行只选一个最值得深入的事件。选题须说明事件为何值得复盘，以及它与 FEEI.CN 既有内容的关系。优先读取已连接 GitHub 的 FeeiCN/FEEI.CN 中 AGENTS.md、仓库写作规范、相关目录和已有文章，核对是否已有同一事件或相近主题，避免重复和覆盖未合并内容。先读取 main 的最新状态。研究只使用公开资料，不接触企业内部机密、密钥、个人敏感信息，不扫描或利用第三方生产系统。

证据标准如下。优先使用受影响组织的官方事件通报、根因分析、技术公告、监管文件、法律文书、漏洞公告、修复提交、版本变更和可复现的公开技术材料，再用高质量独立调查或研究补充。对关键事实至少寻找一份独立佐证，区分已确认事实、来源单方主张、研究者推断和无法确认的部分。不要把多篇转载当作多份独立证据。记录事件发生时间与披露时间，影响范围、损失或数据规模只在来源明确时表述。对争议点保留不确定性并解释它对结论的影响。

复盘框架需要覆盖以下内容，但按事件实际情况组织，不机械套模板。事件背景与业务边界，攻击或故障的时间线，攻击者能力和入口，关键资产、身份、权限与信任边界，技术根因和促成条件，为什么既有控制没有阻止或及时发现，检测与应急响应过程，遏制、恢复、补偿和对外沟通，后续修复是否真正改变了风险，组织职责和治理机制中暴露的问题，可迁移的架构与工程措施，仍然存在的残余风险，以及可以复现或验证的检查方法。需要时给出时间线、控制点、架构图、代码片段或比较表。所有推断都要标明依据和边界。

每月第一周增加一次跨案例复盘。把本次案例与过去三个月已研究的案例进行比较，识别重复出现的失效模式、有效控制和仍未解决的系统性问题，形成一段可以指导企业安全建设的综合判断。没有新增可核验事实或可执行分析时继续研究或更换案例，不发送“无新增”通知。

最终交付完整文章，在本次指定审阅渠道展示从标题到结尾的全文。文章应独立可读，标题直接表达事件和核心判断，不使用“研究周报”作主标题，不用提纲、摘要、占位符或流水账代替正文。采用自然小标题和完整语义段落，避免一句一段和编号堆叠。引用紧邻关键事实，正文给出来源链接或规范引用，准确区分事实、分析和推断。文章篇幅以讲清机制和复盘判断为准。文末注明“完整待审稿，尚未写入 FEEI.CN”，并建议应新建还是完善哪篇文章，但不要提前修改仓库。
