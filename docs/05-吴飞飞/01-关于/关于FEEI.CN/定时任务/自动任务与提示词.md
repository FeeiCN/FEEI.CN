这些任务由独立 GitHub Actions 定时触发，共用执行器。提示词在本目录维护，各任务的 workflow 维护任务 ID、时间、权限、启用开关、提示词路径和交付方式，通过 `with` 传给共用执行器。完整提示词仅在文档中维护，不再另设任务注册表或 ChatGPT 任务清单。旧的两个 ChatGPT 总入口已移除，避免重复执行；已有 ChatGPT 私人任务不由本仓库自动停用。

执行器先校验任务 ID、提示词与启用状态，再执行任务，核对结构化结果和真实交付文件。日记提示词同步检查直接运行确定性脚本，不安装或调用 Codex；其余任务使用模型。`completed` 表示本次任务产物满足要求，`no_update` 表示已检查但没有实质更新，`blocked` 表示缺少核心数据、能力或权限。workflow 触发、job 成功和任务成果达标是不同状态。

各任务使用独立 `AUTOMATION_*` 仓库变量，可分别暂停；提示词读取与结果验证由 `scripts/automation_tasks.py` 完成。运行结果包含提示词摘要、实际执行 commit、触发 commit、来源与核验摘要，记录数据截止时间及历史去重依据。无更新时不发 Issue，仍保留摘要和30天 Actions 附件。知识库治理与研究稿使用“待审阅”标签，生成壁纸等可直接使用的成果使用“已交付”。研究文章仍须确认具体版本后才能写入，定时启用不等于自动发布。

定时触发可能延迟；执行器检出最新 main，分别记录触发和执行版本。港股提醒只在按当前配置推算的最近时段后45分钟内开始，交付前再检查截止时间；过期只留调度检查附件，不发过时提醒。此推算不代表 GitHub 的原始排队时长；手动运行不受该窗口限制。

任务入口、执行约定和提示词集中在「网站幕后 → 定时任务」；仓库协作规范集中在同级「SKILL」。页面不再重复显示分类徽标。

## 执行配置

模型名使用仓库 Variable `OPENAI_MODEL`，当前设为 `gpt-6-astra`；连接凭证与端点继续使用 Secrets：`OPENAI_API_KEY`、`OPENAI_BASE_URL`。不在文档或日志中保存凭证。模型任务执行时不提供 GitHub 写入令牌；模型完成后由固定交付步骤创建审阅 Issue，不自动改文章。

执行器使用独立权限配置：仓库只读，`output/` 可写，允许研究所需的外网访问。每次模型任务运行先在同一配置下实际验证这三项；不能只设置 `web_search` 就假定模型连接具备浏览能力。

四项研究文章任务采用有明确目标和停止条件的写作循环：先形成写作简报与完整初稿，再独立调用模型审稿，必要时最多修订两轮，每版修订后重新复核。审稿核对事实、逻辑、可读性和重要内容是否保留，意见包含具体位置、问题、修改方向及验收条件。初稿达标即停止；可选的风格偏好不触发反复润色；存在关键问题、时间预算用尽或修改停滞时不标为完成。运行预算30分钟，包含研究、写稿、审稿和修订。

目标、简报、各版正文与审稿意见保存在 `output/writing/`，随研究结果作为30天 Actions 附件保存；Issue 交付最后通过模型复核的完整待审稿，仍须本人确认具体版本才写入网站。这是由 `scripts/run_automation_task.py` 顺序控制的执行循环，不依赖交互会话的 `/goal` 状态；新的 Actions 运行通过 Issue 历史延续上下文。阶段提示词集中在[共用执行约定](./自动任务执行约定.md)，其他任务继续单次执行。

健康趋势、体重壁纸和每日个人记录也交付到当前公开仓库的 Issue，用户已明确授权公开这些任务成果，不再需要私人仓库或专用令牌。壁纸只通过 Actions 附件提供 PNG、SVG 下载，需登录 GitHub，保留30天；过期或运行被删除后需重新生成，不长期存图，不上传 Release、网站或其他图床，Issue 不提供内嵌预览。跨 job 的临时交付包保留1天，供下载的纯图片附件保留30天。壁纸交付仅需 Contents 读取、Issues 写入及核验来源所需的 Actions 读取权限；模型执行仍为仓库只读。公开交付不自动发布网站文章，也不上传原始健康数据分片和无关缓存。

每项任务的 `AUTOMATION_*` 变量设为 `true` 后允许执行。手动运行与定时运行读取同一份文档提示词、使用相同权限；验证不能仅检查 workflow 是否触发，还应打开对应运行及成果，核对来源、数据日期、交付正文和实际附件。

所有任务 checkout 到 `$GITHUB_WORKSPACE/feei.cn`，命令默认工作目录为 `feei.cn`；模型执行显式传入 `codex exec --cd "$GITHUB_WORKSPACE/feei.cn"`，并核对 Git 根目录。壁纸模型只准备带日期、单位和来源的 `output/wallpaper-data.json`，由 `scripts/render_weight_wallpaper.py` 统一渲染，版式不随每轮生成变化。同步检查使用 `python3 scripts/automation_tasks.py verify-sync --task diary-prompt-sync`，通过时静默，配置缺陷按 blocked 交付。

Mac mini 的资产、港股与健康导出使用独立 job，手动选择 all 时依次执行，单项失败不取消其他项。健康导出先探测 Health Auto Export 服务，仅在服务不可用时检查 iPhone 并尝试恢复；若设备锁定妨碍恢复，仍需本人解锁。大模型用量按来源报告成功、跳过或失败；已配置来源失败会使任务失败，同时保留其他来源成功导出的数据。

## 手机睡眠评分归档

手机 Shortcut 每天创建“睡眠评分”Issue 后，由「睡眠评分议题归档」自动解析 OCR 并保存到现有 `/data/sleep-score/YYYY/MM/DD.json`；日期取 Issue 创建时间的北京时间自然日。同一天多次提交时，创建时间较新的 Issue 覆盖当天旧评分及细节，原始输入全部留档；重跑较旧 Issue 不会把数据改回。该流程不调用模型或操作手机。它保留评分分项、就寝信息与手表关机提示，校验总分和分项合计，再持久化、更新趋势索引、核对线上数据，最后在原 Issue 回复实际 URL 并关闭。解析失败、版本过期和线上未核验时保留 Issue 供修正或重试，每小时补处理未归档记录。

新数据与原始 OCR 存在服务器，部署不会覆盖该目录，Git 中历史仅作初始化种子。每日个人记录和健康趋势研究自动取得评分与质量提示，和 v5 健康日索引按日期关联，缺失的睡眠阶段和精确时长不补造。格式与合并规则见[健康数据存储规范](../SKILL/健康数据存储规范.md)。

## 阅读输入与成长回访

每日阅读精选直接在 Issue 正文交付一篇完整作品：中文给完整原文，其他语言默认给完整中文译文并标注 AI 翻译，同时保留作者、出处、许可、粗估阅读时间、简短推荐理由和一个读后问题。只选已核验允许转载和翻译的开放授权或公版作品，免费可读不等于允许转载；全文不能由简介、链接或附件替代。选材兼顾长期主题与陌生领域，不只追 AI、安全和投资热点；优先实际打开全文、可直接阅读的来源，按原文和核心问题与历史去重。模型写入 `output/reading-content.json`，程序核对全文文件、授权类型与来源后直接展开正文，过长时不截断。没有合适新材料时静默。

每周阅读回访读取精选议题与本人的真实反馈，追踪一个理解或应用问题，以及本人明确同意的一个小尝试。两项任务在准备和原 Issue 讨论时均提供关联任务历史，跨运行通过 Issue 延续；检索缺口如实保留。没有本人反馈且历史完整时，程序直接跳过模型并保持静默；历史读取不完整时不能声称没有反馈。推荐、收藏、阅读时长和机器人总结都不代表读完、理解或成长。

可在原 Issue 自然回复“这里没懂”“这个观点不成立”“读完了，我想到……”。助手先讨论原文与本人问题，不自动安排练习、记为已掌握或写入网站。后续选材读取这些反馈，保留探索空间；长期规则变更与网站发布仍需单独确认。启用变量分别为 `AUTOMATION_DAILY_READING_SELECTION` 和 `AUTOMATION_WEEKLY_READING_REVIEW`。

## 在原 Issue 中审阅与写入

[历史人物一生决策](./历史人物一生决策任务提示词.md)使用独立的持续会话流程：一个人物保留一个 Issue，由本人自然回复推进，正文维护当前位置与章节索引，评论保存完整故事、选择原话、分析和恢复进度。默认可承接朱元璋避乱与投军的已有讨论；每幕允许多轮追问，决定后与真实历史对照，之后沿真实经历继续。暂停、回看和背景补充不推进章节；没有回复时等待。该类议题由专用 workflow 处理，旅程中的认可与继续不会进入文章审批和网站写入。

新 Issue 标题直接使用成果主题，不带“自动任务”、completed 等执行状态或运行时间；任务分类和交付状态使用 label。

所有自动任务的报告均可在原 Issue 中继续处理，不必复制到本人新建的 Issue。驱动器验证机器人作者、任务标记、当前仓库运行链接及对应 workflow；只有仓库本人发出的评论可以启动审阅和批准。自然语言为默认交互方式，命令保留兼容。本人创建的 Issue 也可直接评论进入相同的内容讨论与审阅流程；首次打开议题和已有普通开发任务的命令入口保留原行为。此自然语言写入入口仍只处理已经展示的完整内容文件，不扩大代码、workflow 或权限修改范围。意图解释器在仓库只读、关闭网页检索的配置下输出结构化判断，不直接执行动作；程序绑定本人最新评论、稿件摘要和内容哈希后再决定后续步骤。

| 操作 | 在 Issue 中发送 |
| --- | --- |
| 提问、比较或讨论 | 直接提问，助手先回答，不强制生成文章 |
| 审阅、修改或优化 | “第二段讲得不清楚，补个例子”；或兼容 `/review`、`/revise` |
| 重新规划写入 | 直接说明希望完善的文章或位置；兼容 `/plan`、`/replan` |
| 首次确认但尚无待审版本 | “整理后写入网站”，先展示完整待写入稿，再确认具体版本 |
| 原报告已封存逐文件完整稿 | “可以，写入”，直接核验该版本并进入写入，无需重复贴稿和确认 |
| 确认具体版本写入 | 展示完整待审稿后明确说“这版没问题，发布吧”等；程序核验对应版本后执行，兼容 `/approve` |
| 使用固定模板重做体重壁纸 | 在原壁纸 Issue 说明“数据同步了，再做一次”等；完成后回复本议题下载链接，兼容 `/regenerate` |
| 暂停 | “先放一放”；以后发新意见可恢复，兼容 `/reject` |

例如，先评论“补读官方根因报告，重新组织因果图，并融入现有文章”，等待助手回复完整修订稿与写入计划，再说“这版没问题，写入网站吧”。“不错”“可以”只表示认可；“按这个改完就发布”先整理新稿，等待再次确认。存在歧义时只澄清必要的问题，不要求改用命令。

助手在审阅阶段只读仓库，联网核对必要材料，并在评论中逐文件展示完整待写入内容，包含 front matter、正文、图和引用。普通问答使用 `codex:discussing`，完整稿待确认使用 `codex:plan-ready`，确实缺少必需事实时使用 `codex:paused` 并说明需要什么。资料不足时先询问缺失事实；日记尤其不能用客观线索替本人补出经历。壁纸重做由单独的固定调度 job 触发原工作流，仅此 job 获得 Actions 写入权限，不让模型自由触发 workflow。准备和交付前均核验机器人任务来源、本人最新请求及其摘要；请求变化或已交付时停止。此入口使用现有模板，不修改绘图脚本，临时附件不能用作网站长期图片。

批准绑定当前 Issue 标题、正文、本人意见和完整待审稿。正文、评论或计划被改动后，旧审批失效；目标文件被 main 更新也须重新审阅。执行阶段只允许修改计划列出的 `docs/`、`blog/`、`static/media/` 文本内容；脚本核对文件与已批准版本逐字一致，再经过文档检查和无警告构建，由 workflow 提交并 push 到 main，根据 workflow 实际结果回复 commit、GitHub 文件链接与验证状态，不把模型执行时尚未构建的描述当作最终交付状态。代码、workflow、组件、原始健康数据及其他计划外内容不能通过此入口写入。

内容写入和数据同步共用 `scripts/workflow_delivery.py` 生成结果回执：文章地址来自本次构建的路由与站点地图，日记和行车记录链接到已存在的对应日记录，阅读、健康、财务与 AI 用量链接到数据看板。回执同时保留提交、文件和运行记录；未找到页面时只给文件入口，不猜测网址。Issue 结果评论与 Actions 摘要使用同一份回执。安全工程同步给目标仓库入口，部署任务单独报告执行结果；提交或同步成功均不代表已经核验线上内容。壁纸仍只提供有保留期限的 Actions 附件下载。

每次运行重新读取原任务、当前正文、全部本人评论、最新完整稿和最近机器人答复，并提供完整当前评论档案与同任务历史供按需读取。意图判断先理解当前本人评论与最新稿件；执行前复核相同判断绑定的请求、稿件和 SHA，不再次让模型重新解释审批。同任务历史搜索最多100个议题，对最近10个读取全部本人和机器人评论，明确记录检索缺口；较早的稿件不会挤掉本人的修改意见。上下文来自仓库和可读取的 Issue，不等于拥有本地 Codex、ChatGPT 或其他会话的记忆。旧意见和旧审批仅作为上下文，不自动成为本版审批。

普通讨论不会直接写入。首次报告若已展示逐文件完整稿，交付程序会将目标文件、main 基线和稿件哈希封存在正文中；本人明确批准即可直接进入验证和写入，不再复制全文索要第二次确认。后续修订稿评论优先于原报告，原报告、本人意见或目标文件变化后仍需核对新版本。确认后的文本由固定程序逐字写入，模型不再参与改稿。尚无完整文件或只有研究正文时，先整理逐文件版本，再由本人确认；第一次确认不能批准之后才生成的内容。旧报告和评论仍兼容原审阅入口。通过具体版本的审批不代表已提交，提交成功也不代表部署成功，应分别核对结果评论、commit 与部署运行。来源无法验证的历史机器人 Issue 会说明阻塞原因，不仅凭标题或标记放行。

### 异常后如何继续

- 审阅失败或资料不足时，先查看运行日志并补充缺失事实，再直接说明希望继续处理的内容；没有完整待审稿时，明确要求写入也只会先整理待审内容，不会直接写入。
- 若意图解释器暂不可用，不会执行写入；稍后直接继续说明要求即可。
- 本人意见、Issue 正文、完整待审稿或相关 main 文件发生变化后，应重新审阅完整版本，再确认本版写入。
- 执行失败时，先核对结果评论、提交记录和部署运行。未提交时排查失败原因，直接补充意见，并审阅完整版本后再确认；已经提交但部署失败时排查或重跑部署，不要再次确认同一版本而重复写入。
