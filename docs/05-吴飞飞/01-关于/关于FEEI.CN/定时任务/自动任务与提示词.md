执行器先校验任务 ID、提示词与启用状态，再执行任务，核对结构化结果和真实交付文件。日记提示词同步检查直接运行确定性脚本，不安装或调用 Codex；其余任务使用模型。`completed` 表示本次任务产物满足要求，`no_update` 表示已检查但没有实质更新，`blocked` 表示缺少核心数据、能力或权限。workflow 触发、job 成功和任务成果达标是不同状态。

各任务使用独立 `AUTOMATION_*` 仓库变量，可分别暂停；提示词读取与结果验证由 `scripts/automation_tasks.py` 完成。运行结果包含提示词摘要、执行 commit 与来源记录。研究文章仍须确认具体版本后才能写入，定时启用不等于自动发布。

## 执行配置

模型名使用仓库 Variable `OPENAI_MODEL`，当前设为 `gpt-6-astra`；连接凭证与端点继续使用 Secrets：`OPENAI_API_KEY`、`OPENAI_BASE_URL`。不在文档或日志中保存凭证。模型任务执行时不提供 GitHub 写入令牌；模型完成后由固定交付步骤创建审阅 Issue，不自动改文章。

执行器使用独立权限配置：仓库只读，`output/` 可写，允许研究所需的外网访问。每次模型任务运行先在同一配置下实际验证这三项；不能只设置 `web_search` 就假定模型连接具备浏览能力。

健康趋势、体重壁纸和每日个人记录也交付到当前公开仓库的 Issue，用户已明确授权公开这些任务成果，不再需要私人仓库或专用令牌。壁纸 PNG 通过公开 Release 地址显示在 Issue 正文中，PNG、SVG 原文件保留下载和历史版本。只有壁纸的交付 job 获得 Contents 写入权限；模型执行仍为仓库只读。图片预览直接引用已上传的公开 PNG，发布重试时复用当前运行对应的 Release。公开交付不自动发布网站文章，也不上传原始健康数据分片和无关缓存。

每项任务的 `AUTOMATION_*` 变量设为 `true` 后允许执行。手动运行与定时运行读取同一份文档提示词、使用相同权限；验证不能仅检查 workflow 是否触发，还应打开对应运行及成果，核对来源、数据日期、交付正文和实际附件。

所有任务 checkout 到 `$GITHUB_WORKSPACE/feei.cn`，命令默认工作目录为 `feei.cn`；模型执行显式传入 `codex exec --cd "$GITHUB_WORKSPACE/feei.cn"`，并核对 Git 根目录。壁纸模型只准备带日期、单位和来源的 `output/wallpaper-data.json`，由 `scripts/render_weight_wallpaper.py` 统一渲染，版式不随每轮生成变化。同步检查使用 `python3 scripts/automation_tasks.py verify-sync --task diary-prompt-sync`，通过时静默，配置缺陷按 blocked 交付。

## 在原 Issue 中审阅与写入

十项自动任务的报告均可在原 Issue 中继续处理，不必复制到本人新建的 Issue。驱动器验证机器人作者、任务标记、当前仓库运行链接及对应 workflow；只有仓库本人发出的评论可以启动审阅和批准。

| 操作 | 在 Issue 中发送 |
| --- | --- |
| 审阅、修改或优化 | 直接评论具体意见，或 `/review`、`/revise 修改要求` |
| 重新规划写入 | `/plan` 或 `/replan`，注明希望完善的文章或位置 |
| 首次确认但尚无待审版本 | 单独评论 `/approve`，自动整理完整待写入稿，展示后再确认 |
| 确认具体版本写入 | 等完整待审稿和目标文件展示后，单独评论 `/approve` |
| 暂停 | `/reject`；以后发新修改意见或 `/review` 可恢复审阅 |

例如，先评论“补读官方根因报告，重新组织因果图，并融入现有文章”，等待助手回复完整修订稿与写入计划，再单独发送 `/approve`。审批评论不夹带新修改要求；先修改、看完整新稿，再确认。

助手在审阅阶段只读仓库，联网核对必要材料，并在评论中逐文件展示完整待写入内容，包含 front matter、正文、图和引用。资料不足时先询问缺失事实；日记尤其不能用客观线索替本人补出经历。壁纸可整理配文与已有附件引用，本流程不改绘图脚本或凭空重画图片。

批准绑定当前 Issue 标题、正文、本人意见和完整待审稿。正文、评论或计划被改动后，旧审批失效；目标文件被 main 更新也须重新审阅。执行阶段只允许修改计划列出的 `docs/`、`blog/`、`static/media/` 文本内容；脚本核对文件与已批准版本逐字一致，再经过文档检查和无警告构建，由 workflow 提交并 push 到 main，回复 commit 与状态。代码、workflow、组件、原始健康数据及其他计划外内容不能通过此入口写入。

普通讨论不会直接写入。尚无可批准的完整待审稿与写入计划时，首次 `/approve` 自动进入审阅，展示具体文件和完整版本后等待再次确认；第一次确认不会批准之后才生成的内容。通过具体版本的审批不代表已提交，提交成功也不代表部署成功，应分别核对结果评论、commit 与部署运行。来源无法验证的历史机器人 Issue 会说明阻塞原因，不仅凭标题或标记放行。

### 异常后如何继续

- 审阅失败或资料不足时，先查看运行日志并补充缺失事实，再评论 `/review`；没有完整待审稿时，`/approve` 也只会先整理待审内容，不会直接写入。
- 本人意见、Issue 正文、完整待审稿或相关 main 文件发生变化后，应重新审阅完整版本，再单独评论 `/approve`。
- 执行失败时，先核对结果评论、提交记录和部署运行。未提交时排查失败原因，重新评论 `/review` 并审阅完整版本后再确认；已经提交但部署失败时排查或重跑部署，不要再次评论 `/approve` 重复写入。
