本文是本站通用文档的写作与审校规则，适用于 `article`、`tutorial`、`reference`、`review`、`hub`、`archive`、`dashboard` 和大多数 `docs/05-吴飞飞/` 文档。`essay` 使用散文写作；入口页、数据页和相册仍需先判断页面职责，再选择对应规则。

## 规则层级与停止条件

先判断页面要完成的任务，再使用相关规则。本文是护栏，不是固定章节模板，也不要求每篇文章包含全部检查项。

规则按强度分为三层：

1. **发布门槛**：页面职责、front matter、事实来源、链接、格式和构建结果必须正确。
2. **内容质量**：论证闭合、机制清楚、证据匹配、边界明确、读者能复用。
3. **表达选择**：标题气质、章节数量、表格数量、结尾方式和句式节奏，只在服务当前读者任务时采用。

当读者任务已经完成、重要事实可以追溯、结构没有明显跳跃且发布门槛全部通过时停止修改。剩余差异属于风格选择，不为了“更完美”继续重写。

## 先写页面契约

新增或结构性重写前，先写下：

```text
目标读者与具体处境：
本文只回答的问题或任务：
读者当前的障碍或已有判断：
核心判断、可复现结果或查询目标：
希望读者读后获得的变化：
页面类型与不承担的职责：
```

一页只承担一种主要职责：

| 类型 | 读者任务 | 完成标准 |
|---|---|---|
| `hub` | 选择下一步阅读 | 说明栏目判断、当前重点和清晰路径 |
| `article` | 理解问题并形成判断 | 机制和证据支撑判断，写出边界和迁移方式 |
| `tutorial` | 稳定复现结果 | 前置条件、步骤、验证、排错和成功信号齐全 |
| `reference` | 查询资料 | 来源、字段、分类、口径和查询路径清楚 |
| `review` | 理解阶段变化 | 结果、原因、错误和下一步调整对应 |
| `archive` | 查看历史原貌 | 保留时间、来源和原始语境，只补必要说明 |
| `dashboard` | 观察持续变化 | 口径、状态、趋势、异常和数据缺口可识别 |
| `gallery` | 浏览媒体 | 媒体为主体，提供最小必要上下文 |
| `essay` | 通过场景理解经验 | 遵循散文写作，以画面和叙事推进 |

入口页不兼任长篇观点仓库，观点文不兼任待办看板，教程不夹带无关行业评论，资料页不为了像文章而增加议论。职责混合时先拆分、下沉或删除，再润色句子。

## 按页面类型组织内容

- `hub` 按阅读选择组织，先告诉读者当前在哪、为什么值得继续、下一步读什么。
- `article` 按判断和机制组织，前几段交代处境、问题和核心判断；结尾留下边界、选择依据或下一步。
- `tutorial` 按操作和验证顺序组织，每一步都能对应一个可观察的结果。
- `reference` 按查询路径组织，优先稳定字段、来源和分类，避免写成散文。
- `review` 按变化与因果组织，区分结果、解释、失误和后续实验。
- `archive` 按时间和来源组织，不用今天的观点改写历史正文。
- `dashboard` 按观察和交互组织，先说明数据口径、缺失和异常。
- `essay` 完全遵循散文写作，不套用本文的“先给结论”与技术论证结构。

## 观点、机制与证据

观点文和解释性复盘可以压缩为：

```text
核心判断 → 成立条件 → 中间机制 → 支撑证据
        → 替代解释或反例 → 适用边界 → 可迁移判断
```

不要求机械分成七节，但最重要的一到三个判断必须能回答：

- 具体主张是什么；
- 结论依赖哪些前提；
- 结果通过什么机制发生；
- 证据观察到了什么，能排除哪些替代解释；
- 何时不成立；
- 读者换一个场景后应检查哪些变量。

证据按句子类型选择：

- **亲历事实**：写清时间、场景、动作和结果，不把一次经历直接推广为普遍规律。
- **外部事实**：优先法规、官方文档、论文、事故披露和原始数据，并标明适用范围和时间。
- **机制判断**：写出中间环节，同时交代不确定性、反例和失效条件。
- **个人选择**：明确是“我的取舍”或“我的做法”，不要包装成普遍处方。

重要判断的强度不能超过证据强度。无法排除反例时，使用“在当前阶段”“对这类系统”“在我可承受的风险范围内”等条件化表达。数字必须有来源、时间、口径、单位、分母或样本量；找不到可靠来源时使用定性表达，或明确标记为待验证估计。模型生成的数字、评分、收益预测、健康效果和法律比例不能直接作为事实。

医疗、投资、法律、安全和快速变化的 AI 内容必须写清适用对象、版本或时间范围、事实来源和行动边界。个人执行方案与通用建议分开。

## 解释和表达

采用“熟悉场景 → 暴露问题 → 命名概念 → 展开机制 → 实例与反例 → 回到应用”的认知顺序。

- 术语首次出现时用一句准确的日常语言解释。
- 每上升一层抽象，就回到一个具体对象、动作、数据或结果。
- 场景和案例必须承担解释功能，展示机制怎样发生。
- 类比只用于建立初始模型，并说明它在哪里失效。
- 保留决定结论的条件和不确定性。
- 直接写清谁做了什么、经过什么机制、产生什么结果。
- 避免空泛口号、虚构普遍焦虑、夸张标题和“不是……而是……”句式。
- 不用“最核心”“最根本”“最终真相”等标题制造确定感。
- `article`、`hub`、`review` 通常使用不超过三级标题；新写的 `article` 通常控制在 5—8 个二级标题，`hub` 通常 3—5 个。
- 标题应表达该节的具体作用；不要使用“背景”“其他”“关键洞察”等无法复述内容的空标题。
- 页面自动处理结构编号，正文标题不手写编号。
- 表格服务于比较和查询；手机阅读困难时拆表或改用列表。
- 图片使用 Markdown title 作为图注，不手写 `figure` 或 `figcaption`。
- 阅读、影视栏目中出现作品名时，标题和 H1 使用书名号。

## 编辑顺序

除 `essay` 和不改正文的 `archive` 外，按以下顺序处理：

1. 定位：确认页面类型、读者、任务和不承担的职责。
2. 立论或复现：确定判断链，或确定操作链与成功信号。
3. 编排：按认知顺序、因果顺序或操作顺序重建章节。
4. 证据：补齐来源、机制、数据口径、反例和边界。
5. 表达：清理术语、重复、空标题和无功能的段落。
6. 对抗审校：寻找最强替代解释、最可能误读和失效条件。
7. 发布：复核 front matter、链接、图片、引用、格式和构建结果。

## 发布门禁

```text
[ ] content_type 与页面职责一致，一页只有一个主要职责
[ ] 新文档有稳定 slug、真实 icon、description、content_type
[ ] description 不超过 160 字
[ ] published_at、引用、数字、版本和外部链接可追溯
[ ] 标题层级、图片、表格和引用符合当前页面类型
[ ] 高风险或高时效内容有适用范围和行动边界
[ ] npm run check:docs 通过
[ ] npm run build 通过；若构建有 warning，已明确处理或记录
```

机器检查只能证明格式和构建状态，不能证明文章值得读。独立冷读或合上正文后按标题复述判断链，是发现结构缺口的最低成本方法。
